# 中国象棋（网页单机版）

浏览器里对弈中国象棋。纯静态 HTML + CSS + JS，无构建工具、无框架、无第三方依赖。
四个挡位的 AI、中文记谱、复盘跳转、悔棋重做、提示、深色模式，
外加一个**局面库**：内置 559 局残局（8 局实用残局 + 551 局《适情雅趣》），
还可以把你下到一半的局面存下来，或者粘贴外部 FEN 导进来。

**长将会判负**：同一局面出现三次本来判和，但如果走成循环的一方**每一步都在将军**，
按棋规**判那一方负**（双方互将则判和）。**AI 也知道这一条** —— 它既不会自己一路将军
走成循环，也会主动把对手逼进去。长捉 / 长兑 / 一将一杀仍然不做（见「关键设计决策」第 10 条）。

**局面也能拿出去**：复制 FEN 给别的软件，或者复制一条**分享链接** ——
别人点开就能直接看到这个局面、接着下。**棋谱也能拿出去** ——
「着法」面板标题右边点一下就复制成一段文本（一行一个回合）。

**残局能「按线走」**：库里 431 局带一条可以跟着走的线（离线用 Pikafish 引擎算出来、
再用本模块的规则层逐步校验过），分两种，**列表和状态行会分开措辞**：

| 徽标 | 局数 | 是什么 |
|---|---|---|
| **有解法** | 397 | 引擎在根上**证明了强制杀**（对手怎么走都杀）—— 可以放心跟着走 |
| **参考线** | 34 | 引擎沿自己选的着法**走到底能杀**，但**前段没有证明** —— 跟着走能到将死，别当正解 |

两种都是：棋盘上方标出这条线，「提示」直接给线上的着法（状态行分别写「谱载解法」/「引擎参考线（非证明）」），
**AI 也按线应着** —— 于是你能顺着那条线一直走到将死。走岔了自动回到引擎搜索，与以前一样。

**也可以不下 AI** —— 侧栏「对局」面板里有个**双人对弈**开关，
打开后红黑两边都由人来点（同一台设备上轮流走）。

棋盘上**轮到谁走，那一方的棋子就带一圈紫色高亮外圈**；
棋盘上方那行状态里的「红方 / 黑方」也跟着上色，不用去读文字就知道该谁走了。
**被将军时**状态行开头写「将军」（红字），棋盘上被将的那个将 / 帅另有一道红圈。

**战斗状态和棋谱说明就在棋盘正上方**（轮到谁走 / 将死 · 谁胜 / 当前是哪一局 · 已走几步）。
不放侧栏是有原因的：窄屏下布局是单列（棋盘 → 工具栏 → 侧栏），
放侧栏会被挤到整页最下面，正在下棋时根本看不见。

## 本地运行

用了 ES Module，**不能直接双击 `index.html`**（`file://` 下会被 CORS 拦掉），
Worker 也需要 HTTP 环境。起个静态服务即可：

```bash
cd treert.github.io
python -m http.server 8000
# 打开 http://127.0.0.1:8000/chinese-chess/
```

部署在 GitHub Pages 上是 HTTP 服务，不受影响。

## 架构

**分两层。** 对局层（`game.js`）是纯逻辑状态机，界面层只负责把它画出来、
把点击翻译成它的调用，自己不持有任何棋类规则。

**状态集中在 `main.js` 的 `app` 对象上。** 其他模块之间不互相 import，
统一通过 `app` 上的回调协作，避免依赖成网 —— 与 `conway-life-game` 同一套做法。

**AI 跑在 Worker 里。** 主线程只发 `{ fen, level }`、收着法。搜索期间主线程禁用操作
（最长 1.5 秒不可中断，见「已知限制」）。

**数据流**：点击格子 → `interaction.js` → `app.onCellClick` → `game.js` 校验并走子
→ `refresh()` → `renderer.draw()` → 若轮到 AI，`worker.postMessage` → 回来再走一步。

## 关键设计决策

每条都记下**否决了什么**，避免以后重复讨论。

### 1. 局面只有一个来源（FEN 字符串）

`game.js` 里不额外维护一份 `Int8Array` 棋盘。需要棋盘时现从当前 FEN `parseFen`（微秒级）。
代价是每次多一次解析，收益是**悔棋、复盘跳转、走子全走同一条路径**，不可能出现
「状态不同步」这类极难复现的 bug。

### 2. 悔棋只移动游标，绝不删除着法

`moves` 数组一直保留，`cursor` 指向「当前在第几步」。所以重做是免费的
（`gotoPly(cursor + 1)`），只有在「回看状态下走新着法」时才截断后面的分支。
每步存一份 FEN 快照（约 60 字符），换来复盘跳转 O(1)；200 步也就 12KB。

### 3. 用 DOM + CSS 渲染，不是 Canvas

这一条**刻意反着 `conway-life-game` 的选择**，因为两个场景的需求正好相反：

- 颜色走 CSS 变量 → **深色模式自动生效，不需要监听 `themechange`**
  （conway 里「页面黑了、棋盘还白着」那个坑在这里直接消失）
- 命中测试用事件委托，免费；格子是 `<button>`，键盘可遍历
- 90 格 + 32 子，DOM 性能完全够

代价：走子动画要靠绝对定位 + `transition` 手写，比 Canvas 里自己实现主题、命中、
无障碍三件事便宜得多。

棋盘是「交叉点」网格：9×10 个格子，每个格子的中心就是一个落子点，
十字线由格子自己的伪元素画。棋盘背景天然自带半格边距，所以边线上的棋子不会被裁掉。

**棋子重绘按格子 diff，不重建。** 同一个格子上还是同一个子，就把那个元素留着；
只有新出现的子才建元素、消失的子才删。省 DOM 只是顺带的，真正的原因是：
元素的 left / top 在插入之前就设好了，所以**重建过的元素不会触发过渡** ——
全量重建会把「正在做过渡的那个元素」删掉重来，过渡当场作废、棋子瞬间落位。
而「同一个任务里连着两次 draw」正好会发生这件事（玩家走完一步，
`requestAiMove()` 里按谱载解法落的那一步是**同步**执行的）。
代价是棋子上的高亮类得自己清：`clearHighlights()` 现在连棋子一起清。

**哪些动作有补间**（`main.js` 的 `stepAnimation`）：刚走完的一步（玩家 / AI）、
重做、悔棋（人机模式一次退两步 = 一个来回，两个子一起滑回去）、
以及着法列表里**相邻**的上一步 / 下一步（列表上方那两个按钮，也是同一件事：
「悔棋」一次退到玩家走，人机模式就是两步；想一格一格翻用这两个）。
跨多步跳转直接落位 ——
要么整盘棋子一起飞、要么得逐步回放等好几秒，两种都读不出「发生了什么」。

**AI 的应手排在补间后面**：`requestAiMove()` 发现棋子还在滑就先等
（`renderer.afterAnimation`），滑完再派发。不等的话，AI 那一步（谱载解法是同步落的、
入门挡位两百毫秒就搜完）会落在玩家的棋子还在半路上时，看着像「没轮到它就动了」。
等待期间**照样占住 `busy`** —— 不然这 200ms 里能点着法列表跳转，
回来 AI 却落在回看状态上，那一步会把后面的分支截掉。

### 4. 挡位是声明式策略表，不是散在代码里的 if

`config.js` 的 `LEVELS` 里，每个挡位是一组参数（`depth` / `quiescence` / `noise` /
`blunderRate`）。想调「第 3 挡再弱一点」，只改表里一个数字。

**四个挡位而不是五个**：深度 6 与 7 对普通玩家体感没有差别，耗时却翻倍。

### 5. 关掉静态搜索是让 AI「像新手」最有效的单个开关

这是挡位设计的核心，有测试正面钉住（`tools/test-engine.mjs`）：

同一个局面（红车可以吃黑卒，但吃完会被黑车吃回）：

- 关掉静态搜索的深度 1 → **贪吃那个卒**
- 开启静态搜索 → **不贪**

关掉静态搜索的 AI 会在兑子序列中途停下、以为自己占了便宜，然后被吃回。
这正是初学者的真实特征，比单纯降深度像得多。所以「入门」和「初级」都关掉了它。

### 6. Worker 不返回记谱

`design.md` §7.4 的初稿让 Worker 在结果里带上 `notation`。实现时去掉了：
主线程在把着法记进对局状态时**本来就要调一次 `toNotation`**（玩家自己走的棋也要记谱），
Worker 再算一遍是重复劳动，还让 Worker 多依赖一个模块。

### 7. 测试策略：不依赖外部基准值

规则层**不用外部 perft 数值**——象棋的 perft 基准值来源不一、容易记错。
改成逐条规则点的断言（蹩马腿、塞象眼、炮的隔子吃、兵过河、将帅照面、应将、
将死、困毙），失败时能直接指出是哪条规则错了。

初始局面着法数拆到每个棋子上断言（5 兵 + 24 炮 + 4 马 + 4 车 + 4 相 + 2 仕 + 1 帅 = **44**），
这样失败时一眼能看出是哪种棋子错了。**这条设计当场就赚回了成本**：手推时把炮数成
11 步、总数写成 42，分解断言直接指出是「炮」这一项错了 —— 漏了「以黑炮为炮架吃掉
它后面的黑马」这一步。

### 8. AI 层只钉稳定的东西，不钉节点数与耗时

AI 单测里**不出现「搜了多少节点 / 花了多少毫秒」**这类断言 —— 它们随机器和时间波动。
只钉三类稳定的东西：纯函数的数值性质、只有唯一正确着法的局面、以及**带对照组的开关**
（只翻一个参数，断言结论变了）。详细分法见 `docs/design.md` §12.6。

自对弈冒烟（`tools/selfplay.mjs`）管的是**状态组合**，单测覆盖不到：

**这个分工被验证过两次**。第一次，`quiesce` 在被将军且一步都走不了时会返回 `-INF`，
取负后变成 `+INF`，而迭代加深判断「找到杀棋」的条件是 `|score| > MATE - 1000` ——
于是把 `-INF` 当成了杀棋、提前停止加深。**54 条单测全绿，因为这个 bug 只在几十手
真实对局里才出现**，冒烟测试一次就抓到了。第二次见 `docs/future-work.md` 的 E9。

### 9. 排局那种十几步连杀，靠「只搜将军」的探测

这是这一版棋力提升的关键，也是唯一一处**为了让引擎看得更远而牺牲完整性**的地方。

- **问题**：常规搜索（哪怕加了将军延伸）在《适情雅趣》第 001 局「气吞关右」那种
  十三层连杀上要**上千万节点、11 秒**，超时线是 1.5 秒 —— 看不见，于是「提示」给出错答案。
- **做法**：常规搜索之前先跑一次「**攻击方只走将军着法**」的强制杀搜索。
  连杀的正解整条都是将军，所以这个限制几乎不丢东西，而节点数从 1100 万降到 **20 万 / 0.75 秒**。
- **它只证明「有杀」，不证明「没有杀」**：攻击方的着法被限制过，找不到不等于没有。
  这个方向恰好安全 —— 找到的杀一定是真杀；找不到就退回常规搜索，什么也没损失。
- **代价用两道闸封住**：层数上限 + 总预算的一部分。没有将军着法的局面是 0 个节点，
  随机中局实测 0~2ms。
- **探测到杀棋时不做挡位弱化**：杀棋是证明不是评估，把已证明的杀棋换成随手一步，
  坏掉的不是棋力，是「提示」的可信度。

实测（**库里还只有前 15 局时**量的）：15 局《适情雅趣》里 **7 局**能被探测直接解出（修之前是 0 局）。
后来残局库补成了全谱 551 局，这个比例没有被重新量过 —— 别把「7/15」当成现在的命中率。

### 10. 循环规则只做「长将」，而且引擎必须看见对局历史

原先只做三次重复判和，于是 AI 把长将当耍赖手段：一路将军走成循环，靠判和收场。
现在按棋规**长将判负**了。这条改动**规则层和 AI 层必须一起改** —— 只改规则层的话，
AI 会照样一路将军，只是从「判和」变成「判自己负」，看起来比原先更像坏了。

- **规则层**（`rules.js` + `game.js`）：判重时看**最近这个循环**里有没有哪一方每步都在
  将军 —— 只有一方 → 那一方负；双方都在将军（互将）→ 判和；都没将军 → 判和。
  循环里「每一步有没有将军」**不额外存字段**，判重时从每步的 `fenAfter` 现算：
  局面只有一个来源，老存档也照样算得出来。
- **只做长将**，不做长捉 / 长兑 / 一将一杀：那几条要逐子比较「捉了谁、比上次重不重」，
  实现和测试成本高一个量级，而长将是普通对局里唯一真会反复出现的一条。
- **AI 层**（`engine.js`）：搜索路径上出现重复局面就按长将给 ±20000 —— 高于任何子力分
  （满盘子力才五千出头），又明显低于 `MATE`（混进「已找到杀棋」那个量级会让搜索提前收手）。
  搜索里按「**第二次**出现」就当作循环成立：棋规要三次，但能原样回来一次就能一直回来。
- **对局历史必须一起发给引擎**，这是这条的关键。只看搜索树是不够的：
  「AI 上一步将军、这一步再将军」这种循环有一半在树外，引擎会以为它随时能收手
  （在树里确实能 —— 它会「让一手」），于是一路将军走到底。
  主线程把整条线的 FEN（`history`）随局面一起发过去，引擎把它接在搜索路径前面。
  Worker 协议见 `docs/design.md` §7.4。
- **代价**：每次搜索多解析一遍历史（一局棋上百步，零点几毫秒）；每个搜索节点多做一次
  「这个局面走过吗」的查询（历史那一段建了哈希索引，O(1)，不随历史长度增长）。

### 11. 位置表是「可分离的两张小表」，不是 630 格手填

用户报过一次「高级 AI 开局第一手走 `炮八进七`（借对方的炮当炮架，一个炮换一个马）」。
查下来不是搜索坏了，是**估值问题**：评估只有子力的时候，开局的每一个安静着法都是 **0 分**，
选哪个纯凭搜索先试到谁；而那一步在浅层看着是赚的（先吃马，「被吃回来」是下一层的事），
于是它总被选中 —— 加上位置表之后这步就没了。

- **表写成「纵线分 + 行分」**（`config.js` 的 `PIECE_SQUARE`），铺成 7 × 90 的查表。
  逐格手填的 630 个数没人复核得了、也没人知道为什么是那个值；可分离的形式下每个数
  都对应一条能讲出来的常识（中路比边路值钱、过河比压底线值钱、炮待在对方底线上是死子…）。
- **左右对称** → 黑方按 y 镜像查同一张表就够；开局那种左右对称的局面两边正好抵消，
  静态评估仍然是 0（`test-engine.mjs` 钉着这条）。
- **兵不另开表**：它的位置分就是已有的过河加分（`PASSED_PAWN_BONUS`）。
- **第一版是手写常识，不是实测表**：将来要从 Pikafish 换算真实位置表，换掉的就是这一块数据，
  `evaluate()` 一行都不用动。

这一条还留下一个教训（记在 `future-work.md` 附录 E）：原先那组长将的**端到端**测试
依赖「几个着法同分时根节点优先试将军」这条**排序**性质 —— 评估一改就判不了对错。
测试该钉的是机制，不是「因为同分所以先试到谁」这种巧合。

## 双人对弈

侧栏「对局」面板里有个**双人对弈**开关，打开后不走 AI：

- 红黑两边都由人来点，棋盘上方的状态行不再说「你 / AI」，只说「轮到红方」
- **「执子」会被禁掉** —— 双人模式下它没有意义（想让黑方在下方，用「翻转」）
- **「悔棋」只退一步**。人机模式会一直退到轮到你走，那在双人模式下会把对手刚走的那手也抹掉
- 「提示」和「挡位」照旧可用 —— 提示是给「当前走棋的人」用的，不专属某一方

开关状态跟着存档走，刷新页面不会丢。

## 常见改动

### 调整某个挡位的手感

改 `js/config.js` 的 `LEVELS`。四个参数的含义：

| 参数 | 作用 |
|------|------|
| `depth` | 迭代加深的上限，实际由 `timeLimitMs` 截断 |
| `timeLimitMs` | 时间上限（毫秒） |
| `quiescence` | 是否做静态搜索。**关掉会让 AI 明显「像新手」** |
| `noise` | 根节点评分扰动幅度。越大越容易走次优着 |
| `blunderRate` | 按此概率故意走次优着（模拟看漏）。只剩一个合法着法时不触发 |

### 提升棋力

**评估方向**：改 `engine.js` 的 `evaluate()` 与 `config.js` 的 `PIECE_SQUARE`。

位置表已经做了（见「关键设计决策」第 11 条），但那是**手写的常识版**：下一步可以从
Pikafish 换算一份实测位置表，替换 `config.js` 里那几个小数组即可，`evaluate()` 不用动。

**不要加「机动性」这类需要生成着法的项** —— 评估在叶节点被调用上百万次，
生成着法等于把搜索成本翻倍。位置表之所以能加，是因为它是 O(1) 查表。

**搜索方向**：改 `LEVELS` 里的 `checkExtension`（将军延伸的层数上限）与
`mateProbePly`（连将杀探测的层数上限）。这两个是「排局连杀」从看不见到看得见的开关，
机制见上面「关键设计决策」第 9 条。加大它们的代价是同样的时间预算下常规搜索浅一层 ——
`config.js` 里写了怎么权衡。

**不顺手的挡位**：还是改 `LEVELS` 里的 `depth` / `timeLimitMs` / `noise` / `blunderRate`。

### 加一个残局

**不想碰代码**：打开页面的「保存 / 导入」，把当前局面存成自定义局面，
或者粘一段 FEN 收进库里。这条路径完全在界面上，不用改源码。
（只想拿粘进来的局面下一盘、不想存，用「载入到棋盘」。）

**想进内置库**：在 `js/endgames.js` 里按格式加一条
（`{ id, name, fen, result, difficulty, source, note }`），
然后跑 `node chinese-chess/tools/verify-endgames.mjs` 校验。详见下面「残局库」一节。

### 改棋盘样式

颜色在 `style.css` 顶部的 `--xq-*` 变量里（深浅两套）。
棋盘的线、河界、九宫分别在 `.xq-cell::before/::after` 和 `.xq-board::before/::after` 里；
外框、楚河汉界、上下纵线号、星位直角是 `renderer.js` 建的 `.xq-deco` 一层，
位置全用 `cqw`（1 格 = 11.111cqw）；纵线号借 `.xq-board` 的上下 margin 站在棋盘外面。

## 已知限制

> 下面是一份**给使用者看的摘要**。完整的清单（含每条的改进路径与工作量估算）、
> 以及「设计里写了但没实现」「实现偏离了设计」的记录，都在
> [`docs/future-work.md`](./docs/future-work.md)。

| 限制 | 说明 |
|------|------|
| **循环规则只做长将** | 长将判负已实现（规则层定性 + AI 侧同步，见「关键设计决策」第 10 条）。长捉 / 长兑 / 一将一杀仍然不做 |
| **重复判定在搜索里提前一次** | 引擎按「局面第 2 次出现」就当作循环成立（棋规要第 3 次）。这是引擎里的标准近似：能原样回来一次就能一直回来 |
| **评估是「子力 + 手写位置表」** | 位置表是「纵线分 + 行分」的手写第一版（常识级：中路、过河、出子、帅不乱动），不是从强引擎换算的实测表。高级挡位大约业余中低水平（连杀例外 —— 那是搜出来的，不是评出来的） |
| **无开局库** | 开局阶段可能不按谱走 |
| **弱挡位看不见一步杀** | 入门 / 初级两个开关都没开（将军延伸、静态搜索），`depth <= 0` 的节点不生成着法，所以看不见。中级 / 高级两个都开着，能看见 |
| **连杀探测只证明「有杀」** | 本地引擎的探测把攻击方限制在将军着法上，所以「找不到」不等于「没有」。**有谱载解法的局不受这条影响**（那是引擎证明过的杀线）；没解法的局仍可能给出错的提示 |
| **AI 思考期间不能中断** | 最长 1.5 秒内禁用操作，不做取消 |
| **走子动画只覆盖「刚走一步」** | 悔棋 / 复盘跳转是全量重绘，没有补间 |
| **棋子字形依赖系统楷体** | 字体栈 `KaiTi → STKaiti → SimSun → serif`，缺楷体的系统会兜底成衬线体 |
| **移动端不做拖拽** | 触屏走「点选 → 点棋盘」两步，避免与滚动打架 |
| **必须走 http 服务** | ES Module 与 Worker 在 `file://` 下都不工作 |
| **残局库的胜负结论未经机器验证** | 实用残局取自教材定式（可靠）；适情雅趣前五卷与「引擎解出杀线」互相印证，卷六逐局核对过通行整理本（改了 29 局，只剩 1 局存疑）。详见「残局库」一节 |
| **部分残局没有解法** | 431/559 局带一条可以跟着走的线：**397 局是已证明的杀线**（「有解法」），**34 局只是「引擎参考线」**（走到底能杀、前段没有证明）。剩下 104 局要么是和局/黑胜、要么引擎既没找到强制杀也没走成完整线 —— 只能靠本地引擎现算，可能给不出答案。详见「残局库」一节 |
| **「参考线」不是正解** | 那 34 局的前段只是引擎的偏好（实测把谱上妙手换成次优着法只差 0.3~0.8 个兵，引擎分不出「杀网还在」和「只是还大优」）。界面三处（徽标 / 棋盘上方 / 状态行）都分开措辞，不会说成「解法」 |
| **不做局面编辑器** | 不能自由摆棋。但可以把**当前局面**存成自定义局面，或者粘一段 FEN —— 收进库里，或者直接载入棋盘 |
| **自定义局面没有结论** | 程序无从知道你存那个局面时的胜负，所以不做「达成目标」判定。想要结论得进内置库（手工标注 + 标明出处） |
| **自定义局面存在 localStorage** | 清浏览器数据 / 换设备 / 换浏览器都会丢，最多存 100 条。想长期保留就把 FEN 抄出来 |

### 卷六的结论：逐局核对过一遍，改了 29 局

（「仕相全对三卒」「车卒难胜单车」…）全被当成了红先胜 —— 它们其实大多是和局研究。
这次把原本标「胜」的 33 局逐局对着通行整理本核了一遍：

- **27 局**实为红先和（改标 `draw`）
- **2 局**实为黑胜（改标 `loss`，界面上显示「先手负」）
- **2 局**确认是红先胜（第 483、493 局，后者还有一条 9 步的杀线）
- **1 局存疑**：第 480 局「三军劫寨」的 FEN 与局名括号对不上（括号说「仕相全对三卒」，
  盘面却是三兵对士象全），通行本标黑胜、引擎又判红方大优。**照原样保留、就地留了注释**，
  没改 —— 拿不准的地方不抹平。原本标「和」的 52 局没逐局核，抽查了 3 局，都一致。

难度也不再是清一色的 5：

| 页 | 依据 |
|---|---|
| 适情雅趣·杀局 | 已证明的杀线长度（`solutions.js` 的 mate 步数）分档；没有解法的记 5 |
| 适情雅趣·和局 | **守和容错** —— 引擎对轮走方每个合法着法各搜一遍，看评分离散度分档 |

### 局号有个坑：从第 227 局起比通行本大 1

本库的「第 N 局」与网上通行整理本（东萍、象棋道、李艾东注本）**差 1**：
原文件在 227 那一带多收了一条「原_227局_舍生取义_补图复原」，之后编号整体后移一位。
所以本库的**第 469 局 = 通行本的第 468 局**，第 551 局 = 通行的第 550 局。
拿局号去别处搜之前先减 1。（通行全谱 550 局、十卷；卷六 = 通行第 467-550 局 = 本库第 468-551 局。）

**别指望这 551 局都能被「提示」解出来** —— 连杀探测只在早期那 15 局上量过命中率（7/15），全谱的比例没测过。

### 第 511 局：题面就是「红方被将军」

第 511 局「内外俱安」的出题局面**红方一开始就被将军** —— 黑炮在 (4,1)、隔着红仕 (4,8)
打红帅 (4,9)，而**谱上就从这儿开始**。

「轮走方被将军」是**合法**局面（他应将就是了），红方 6 个合法着法都能解：
`车六平五`（往炮与帅之间再塞一个子，炮就多了一个架子、打不着了）、
`仕五退四 / 仕五退六 / 仕五进六`（抽掉炮架）、`帅五平六 / 平四`（躲开）。
实测四个挡位都能给出应将着，局面有真正的解法。真正非法的只有「非轮走方被将军」，
那条在 `isLegalPosition` 里。

**另外，这一局的数据本身有个疑点**：题名说黑方是「双炮」，盘面却是「车炮」。
它和第 510 局「车双相和车炮」是相 / 仕一对（黑方炮 (4,1) + 将 (5,1) 完全一样），
题名多半是「车炮」误作「双炮」—— 全谱题名带「双炮」的另外 6 局，盘面都对得上。

**照原样收录，一个字没改。** 谱载结论「和」也照标 —— 它本来就在「和」那一批里，
不在后来改标的 29 局中，但也没有单独逐手验过。拿不准的地方要留痕，不能顺手抹平。

标题右边的「局面库」按钮打开弹窗（按钮上会显示你现在在哪一局），
里面按页签分好类（实用残局 / 适情雅趣·杀局 / 适情雅趣·和局 / 自定义），点一局即可载入。
载入后棋盘上方会显示**谱载结论**与**已走步数**，终局时判定「达成目标 / 未达成目标」。
想回普通对局，点弹窗里的「退出残局」。

**页签下面有个过滤框。** 551 局光靠滚是找不到具体一局的，所以可以按**局号或局名**过滤
（「473」「中外」「473 中外」都行 —— 空白分隔的多个词是「与」）。三条约定：

- **只匹配名字，不匹配 FEN。** 名字是列表上唯一显示出来的文本；命中了看不见的字段，
  用户只会觉得「这行为什么会在这儿」。
- **它只在当前页签内生效**，不跨页签搜。跨页签的线索改由**页签徽标**给：有过滤词时
  徽标显示的是各页的命中数，所以「要搜的东西在别的页签里」一眼就能看出来。
- **Esc 是两级的**：先清掉过滤词，框空了之后再按才关弹窗。过滤词不跨「打开弹窗」这个动作活着 ——
  下次打开还是完整的一页。

这个弹窗**只管挑**。往库里加东西是另一件事，入口在标题行右边的**「保存 / 导入」**
（见下面「自定义局面」一节）。

### 数据来源与授权

「适情雅趣」这两页取自 [`kuiba1949/xiangqi-tools`](https://github.com/kuiba1949/xiangqi-tools) 的
`fen/shiqingyaqu551.fen`（BSD-3-Clause）。原文件每行形如：

```
[FEN_INDEX "shiqingyaqu-551-001"] [EVENT "...第001局 气吞关右"] [FEN "..."]
```

本模块把 `FEN_INDEX` 用作 id、`EVENT` 里的局号局名用作 name。
**FEN 原样照抄、一个字符都没改**；id 和局名有**三处**人工整理，都不涉及局面本身：

1. 去掉原文用来标记补图 / 异文的 `*`（局名里的，如 `*第002局 马蹀阏氏` → `第002局 马蹀阏氏`）
2. 原文唯一一条没有局号的记录 —— id 是 `shiqingyaqu-551-228plus`、`EVENT` 是
   `*原_227局_舍生取义_补图复原`（原第 227 局「舍生取义」的补图复原版）——
   这里写成 id `shiqingyaqu-551-227`、局名「第227局 舍生取义（补图复原）」，与「第227局」对齐
3. 第 543 局的局名在括号前补了个空格（原文 `固前遮后(` → `固前遮后 (`）

**第 2 条那条记录，正是「局号比通行本大 1」的原因** —— 它把后面所有编号顶后了一位，
所以本库的第 469 局才是通行本的第 468 局（详见上面「局号有个坑」）。

《适情雅趣》是明代排局谱，属**公有领域**；该仓库的 FEN 转换部分按 BSD-3 授权。

**运行时绝不联网** —— 上面的数据已经一次性整理进 `js/endgames.js`。

### `result` 字段的可靠性边界（重要）

要证明「红先必胜」需要可靠的求解器或权威棋谱，本模块的引擎（简化评估 + 迭代加深）做不到。所以：

- **实用残局**：结果取自教材定式，可靠
- **适情雅趣·杀局**（前五卷）：谱上标「红先胜」，与「引擎解出杀线」互相印证（388/467 解出）
- **适情雅趣·和局**（卷六）：原本标「胜」的 33 局逐局核对过通行整理本（见上）；
  原本标「和」的 52 局只抽查了 3 局

**没有一条结论是机器验证过的。** 「和」与「黑胜」尤其证不出来 —— 要证的是一棵
「守方每步都不输」的与或树，象棋里工程上做不到。`verify-endgames.mjs` 只校验局面合法性、
**不校验胜负结论**。每局都带 `source` 标明出处，结论留给你实战验证。

### 解法（`js/solutions.js`）与参考线（`js/prefixes.js`）—— 离线生成的数据

**两份数据、一种用法、两种可信度**：

| 文件 | 字段 | 内容 |
|---|---|---|
| `js/solutions.js` | `src: 'mate'` | 引擎在根上**证明了强制杀**的完整杀线（397 条） |
| 同上 | `src: 'walk'` | 引擎**走到底能杀**、但前段没有证明的完整线（34 条） |
| `js/prefixes.js` | — | 引擎首选前缀：没走成杀的局给「前 N 回合」（58 局，含上面那 34 局的整条线）。**排除三类**：引擎认为红方不行的（020 / 190 / 267 那批"反杀"局 —— 那条线是黑方将死红方）、走两步就掉到 +1.5 兵以下的（那批赢不下来）、以及已经有已证明解法的 |

用户能感觉到的行为（两种来源共用同一套机制）：

- 棋子库列表里带徽标：**「有解法」**（`src='mate'`）/ **「参考线」**（`src='walk'` 或只有前缀）
- 棋盘上方标出这条线的说法：「有解法（N 步杀）」/「引擎参考线（走到底 N 步杀，前段未经证明）」
- 点「提示」**直接给线上的着法**（不必等引擎，省掉最长 1.5 秒），状态行分开写
  「谱载解法」/「引擎参考线（非证明）」
- **轮到 AI 时也按线应着**。这不是可选装饰：玩家刚走一步、对手就走到线外去的话，
  那条线根本走不完。AI 按线走，等于陪你把这一局「演」完
- 一旦走了线外的着法（走岔），**自动回退引擎搜索**，与没有线的局完全一样

**参考线为什么不能叫「解法」**：它的前段只是**引擎的偏好**。实测第 004 局把谱上的妙手
`炮五平一` 换成次优着法，Pikafish 只差 0.76 个兵（+9.52 vs +8.76）——
**它分不出「杀网还在」和「只是还大优」**。所以那一批只能这么标，措辞、徽标、tooltip 三处都分开写。

数据是**离线的产物**：`tools/gen-solutions.mjs`（解法）与 `tools/prefix-scan.mjs`（参考线）
驱动 Pikafish（外部 UCI 引擎）生成，`tools/verify-solutions.mjs` 用本模块规则层逐条校验
（每步合法 + 末局将死 + 长度自洽）。引擎与权重不进仓库，运行时零依赖、不联网 ——
与 FEN 一次性整理进 `endgames.js` 是同一套做法。
操作手册（下载、命令、坐标换算、手动验局的现成配方）见 [`docs/pikafish.md`](./docs/pikafish.md)。

**为什么是「引擎算的」而不是「古籍原谱」**：网上流传的 PGN 授权不明、链接易失效，而且那份
解法本身也是老引擎（EleEye / sjaakii）跑出来的。自己跑的好处是授权干净、可复现；
代价是**个别局面给出的是与谱载等价的另一条杀线**（都能杀，只是着法不同）。

**剩下 104 局没有任何线**（其中 80 局是谱载和棋、2 局黑胜 —— 它们本来就没有「正解着一说」）
**不给编**：查不到就明说没有，照旧走引擎搜索。

> 生成过程中撞出 **3 局「谱载胜、引擎判定红方被杀」**（第 020 / 190 / 267 局；
> 另外两局第 496、506 局核对下来本来就是黑胜，不算矛盾）。
> **全部没解出来的局**都列在 [`docs/pikafish-unfinished.md`](./docs/pikafish-unfinished.md) 里，
> 按「该不该人工核查」分成三组（反杀 / 评估≈0 / 大优但无杀），另附和局与黑胜备查 ——
> 这批就是「结论未经机器验证」那笔账的第一批具体线索。

### 加一局 / 改一局

1. 在 `js/endgames.js` 里按格式加一条（或改某一局的 FEN）
2. 跑中控流程：`node chinese-chess/tools/solve.mjs --ids <这一局的 id>`

`solve.mjs` 会把整条链路跑一遍：校验局面 → 引擎找杀（快轮 + 慢轮）→ 走到底 →
规则层复核候选线 → 写 `solutions.js` / `prefixes.js` → 校验 → 更新「没解出来」清单，
失败即停并告诉你哪一步失败、怎么单独重跑。**加/改局面只需要这一条命令。**

```powershell
node chinese-chess/tools/solve.mjs --ids my-new-endgame     # 新加 / 改过 FEN 的局
node chinese-chess/tools/solve.mjs                          # 补跑所有「还没解法、账本里也没记录」的局
node chinese-chess/tools/solve.mjs --status                 # 只看现状（不开引擎）
node chinese-chess/tools/solve.mjs --ids my-new-endgame --dry-run   # 只打印要跑的命令
```

**注意 `--ids` 会带 `--force`**：账本按 id 存，改了 FEN 之后不带 force 的话，
「走到底」那一步会直接跳过它（跑的还是旧局面）。不带 `--ids` 时故意不带 force ——
那样只补「还没有记录」的局。

只想手动跑其中一步也可以（`--dry-run` 会把每条命令打出来），见 `docs/pikafish.md`。

**这个脚本是有用的，不是走过场**：实际开发时它抓出了一局 FEN 把「将」和「士」的位置写反了 ——
结果黑将与红帅同在一条纵线上（照面），是个非法局面。只靠肉眼看 FEN 很难发现。

它还会挡住「把强弱写反了」这类错误，但**只对实用残局查子力一致性**：
《适情雅趣》前五卷的排局恰恰以「红方子力更少、靠连杀取胜」为常态，卷六的和局研究更是
「弱子守强子」，把它们也拦下来是错的。

## 自定义局面

局面库弹窗里有个 **「自定义」页签**（带条数徽标），那里放你自己存的局面。
相关的入口按**动作的性质**分在三处：

| 想干什么 | 去哪 | 怎么做 |
|----------|------|--------|
| **挑一局来下** | 标题行左边「局面库」 | 选页签 → 点一局 |
| **把 FEN 框里那个局面收进库里，以后反复练** | 标题行右边「保存 / 导入」 | 起个名字 → 「存为自定义局面」。**框里打开时就是当前局面**，不动它就是存当前这盘棋 |
| **把 FEN 框里那个局面摆到棋盘上，接着下** | 标题行右边「保存 / 导入」 | 「载入到棋盘」。**不进库**，棋盘换成一个「临时局面」 |
| **把当前局面拿出去** | 棋盘下方工具栏「复制 FEN」/「复制链接」 | 点一下就复制（按钮会短暂显示「已复制」）。剪贴板不可用时会把内容填进「保存 / 导入」的框里，手动复制即可 |
| **把这盘棋的着法抄出来** | 侧栏「着法」面板标题右边「复制」 | 复制成一整段文本，一行一个回合（`1. 炮二平五 马8进7`）。抄的是列表里**全部**着法，回看状态下也是（列表显示多少就复制多少）。一步都没走时按钮是灰的 |
| **给存过的局面改个名字** | 标题行左边「局面库」→「自定义」页签 | 点那一行右边的 **✎**。只改名字，局面本身不动 |
| **删掉一个存过的局面** | 同上 | 点那一行右边的 **✕**（删之前会问一次） |

**「保存 / 导入」里只有一个 FEN 框。** 打开时框里已经填好**当前局面**（并且是全选状态），
所以「存当前这盘棋」和「存别处的局面」是同一个动作 —— 不动它就是当前局面，
把别处复制来的 FEN 粘上去覆盖掉，就换成了那个局面。然后才选去处：
**存为自定义局面**（收进库）或者 **载入到棋盘**（不进库）。

**框里就是当前局面时，「载入到棋盘」是灰的** —— 那种情况点了等于没点。
两个细节：判「是不是同一个局面」用的是**规范化之后**的 FEN（尾部几个字段写成 `w - - 12 34`
也算同一个）；**解析不了的 FEN 不禁用** —— 点了会告诉哪儿不对，禁掉的话用户只知道按钮坏了。

> 这里原来拆成「存下当前局面 / 导入外部局面」两段，结果是两个都叫「存为自定义局面」的按钮
> 并排出现（一个存当前局面、一个存粘进来的 FEN）—— 看着像重复，其实是一件事：局面就是框里那个。

**列表里每一行右边有两个小按钮**，只有自定义局面才有（内置残局是代码里的数据，改了删了下次刷新又回来）：
**✎** 改名字、**✕** 删除。改名只动名字，局面本身一个字符不碰；改完列表、标题行、棋盘上方那行目标会一起变。

**为什么这么分**：这几个动作的**方向不一样** ——「挑」是读；
弹窗里那几个是「进」，但**进的地方不同**（存进库里反复练 vs 摆到棋盘上接着下）；
「复制 FEN / 复制链接」是「出」，而且是个即时动作（和悔棋 / 翻转同类），
做成按钮比塞进弹窗更直接。

**复制 FEN 和复制链接的区别**：前者给你一段文本（贴进别的软件、棋谱），
后者给你一条链接（对方点开就是这个局面）。链接**只带局面** ——
不带这盘棋的着法历史，也不覆盖对方的挡位和执子方。
语义是「来看这个局面」，不是「来看我下的这盘棋」。

**复制着法**是第三个「出」：给的既不是局面也不是链接，而是**这盘棋的过程**。
它的按钮没放工具栏，放在「着法」面板自己身上 —— 复制的是那个列表，
按钮就该长在列表旁边（工具栏上那几个都是「对棋盘上这个局面做点什么」）。

### 「临时局面」：不进库的那个

分享链接打开的局面，和「载入到棋盘」摆上来的局面，都是这一类 ——
它既不是内置残局、也不是你的自定义局面，所以：

- 标题行显示成**「临时局面」**，并给一行「退出，回到标准开局」
- 它**会进本地存档**，刷新照样在（「不进库」指的是不进**自定义局面列表**）
- 想留着的话，用「保存 / 导入」把它存成自定义局面

**链接里的参数读完就抹掉**（`history.replaceState`）—— 留着的话，
之后每次刷新都会把你从「自己后来选的局面」拽回分享的局面，那看起来很像 bug。

### 两道校验，松紧不同

框里那个 FEN 先过第一道，过了再看你要拿它干什么：

| | 「载入到棋盘」 | 「存为自定义局面」 |
|---|---|---|
| FEN 能解析、局面合法 | 要 | 要 |
| 轮走方有合法着法 | **不查** —— 摆上去看看完全合理 | **要** —— 已经终局的局面没有练习价值 |
| 规范化（尾部统一成 `- - 0 1`） | 要 | 要 |

**「轮走方正被将军」两道都不拦。** 那是合法局面（他应将就是了），
「我正被将、该怎么解」本来就是正当需求 —— 摆得上去，也存得下来。

存进库还要过名字那两道（非空、不超长）和去重（同一局面不重复存），
任何一道不过都会把**原因**显示在弹窗底部。

**自定义局面没有「结论」。** 程序无从知道你存那个局面时的胜负，
硬标一个「先手胜」就是编造事实 —— 而且会和内置库那批本来就「逐局未复核」的结论混在一起，
让人以为它是可信的。所以界面只显示「自定义局面」，不做「达成目标」判定。

**存储位置**：localStorage 的 `chinese-chess:endgames`，最多 100 条。
清浏览器数据 / 换设备 / 换浏览器都会丢 —— 想长期保留就把 FEN 抄出来存到别处。
