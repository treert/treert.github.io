# 中国象棋模块 · 开局库

**这是什么**：一张**手写的开局着法表**。局面在表里、且挡位允许时，AI **直接走谱上的着法，
不做搜索**。

**它解决什么**：`future-work.md` 的 **C7（开局库）**，以及 README「已知限制」里的
**「无开局库 —— 开局阶段可能不按谱走」**。

- 代码：[`js/openings.js`](../js/openings.js)（数据 + 索引 + 查询）、
  [`js/iccs.js`](../js/iccs.js)（ICCS 坐标换算，和解法共用）
- 引擎接线：[`js/engine.js`](../js/engine.js) 的 `search()` 开头
- 测试：[`tools/test-openings.mjs`](../tools/test-openings.mjs)

相关文档：[`design.md`](./design.md) §7.2 / §7.3 / §7.5、[`decisions.md`](./decisions.md) 第 12、13、14、15 条、
[`future-work.md`](./future-work.md) C7。

---

## 1. 为什么需要它：位置表管「不像话」，开局库管「不像人」

这两件事必须分开看，否则一定会改错地方（`future-work.md` C1 的教训：

> **「棋盘力不够」时先分清是「估值问题」还是「视野问题」。**

| 症状 | 例子 | 该改哪 |
|------|------|--------|
| **估值问题** | 高级挡位开局第一手走 `炮八进七`（借对方的炮当炮架，一个炮换一个马） | 评估 —— 位置表 / 相位（`config.js` 的 `PIECE_SQUARE_*`） |
| **视野问题** | 《适情雅趣》那种十几步连杀看不见 | 搜索 —— 将军延伸、连将杀探测（`engine.js`） |
| **「不像人」问题** | 开局走的每一步都合法、估值也不算错，但**人不会那么走** | **开局库**（本文档） |

位置表让 AI 不再走明显亏的着法，但**它给不出人类的开局共识**：中炮、屏风马、仙人指路、
飞相局……这些是几百年实战筛出来的东西，浅层搜索不会自己发现。开局库就是把这份共识
**直接写下来**。

> 分工：**位置表 / 相位让 AI 不犯傻，开局库让 AI 像个人。**
> 两者不冲突，也不互相替代。

## 2. 数据长什么样

一条线一行，写在 `js/openings.js` 的 `LINES` 里：

```js
{ name: '中炮对屏风马', weight: 3, moves: 'h2e2 h9g7 h0g2 i9h9 i0h0 b9c7 c3c4 g6g5' },
```

| 字段 | 含义 |
|------|------|
| `name` | 这条线叫什么（顺炮 / 屏风马 / 仙人指路…），只给人看，不参与逻辑 |
| `weight` | **相对权重**（默认 1）。同一个局面下有多条线给出不同着法时，权重决定挑到它们的概率 |
| `moves` | 从**标准开局**开始的一串着法，**红先、红黑交替**，用 **ICCS 坐标**写 |

### ICCS 坐标

列 `a`-`i` 从左到右（`x = 0..8`），行 `0`-`9` **从红方底线往上**。
本模块内部 `y = 9 - rank`。换算在 [`js/iccs.js`](../js/iccs.js) 里，和解法
（`solutions.js`）**共用同一份** —— 这样数据能拿去和任何棋谱对照，也能直接喂给引擎。

几个常用锚点（写数据时对着这个核对）：

| ICCS | 棋盘位置 | 中文记谱 |
|------|----------|----------|
| `e0` | 红帅（九宫中心，红方底线） | — |
| `e9` | 黑将（九宫中心，黑方底线） | — |
| `h2e2` | 红炮从 (7,7) 到 (4,7) | **炮二平五** |
| `h9g7` | 黑马从 (7,0) 到 (6,2) | **马8进7** |
| `c3c4` | 红兵从 (2,6) 到 (2,5) | **兵七进一** |
| `g0e2` | 红相从 (6,9) 到 (4,7) | **相三进五** |

### 现在库里有什么：两半数据

**库里有两半**，走同一条入库路径（`indexLines` / `indexGenerated`），撞到同一个局面时权重相加 ——
也就是「手写线和引擎都说这一步好」：

| 哪一半 | 在哪个文件 | 怎么来的 | 规模 |
|--------|-----------|----------|------|
| **手写的线** | `js/openings.js` 的 `LINES` | 人写的常识 | **7 条线 / 25 个局面** |
| **生成的谱** | `js/openings-generated.js` | `tools/gen-openings.mjs` 驱动 Pikafish 离线展开 | **1,789 个局面 / 3,492 条候选** |

手写那 7 条（**归一后**的键数；互为左右镜像的局面算同一个）：

| 线 | 手数 | 权重 |
|----|------|------|
| 中炮对屏风马 | 8 | 3 |
| 中炮对顺炮 | 6 | 2 |
| 中炮对列炮 | 6 | 1 |
| 中炮对单提马 | 4 | 1 |
| 仙人指路 | 4 | 1 |
| 飞相局 | 4 | 1 |
| 起马局 | 2 | 1 |

合并后索引里一共 **1,794 个局面**（两半重叠 20 个）。

**深度到第 8 个半回合为止，而且是刻意的。** 再深，变例树按层数指数膨胀（每层乘两三倍），
边际价值却很低 —— 谱外的事只能交给搜索。一份参考量级：每一层**需要应着**的局面数，

| 第几手之前 | 1 | 2 | 3 | 4 | 5 | 6 | 7 | 8 |
|---|---|---|---|---|---|---|---|---|
| 手写那半 | 1 | 4 | 7 | 6 | 6 | 3 | 3 | 1 |
| 生成那半 | 1 | 3 | 15 | 57 | 155 | 280 | 471 | 807 |

深水区的差距就是这么来的（第 8 手前 807 对 1）。

### 只写右手那一半：左右镜像归一

棋盘左右对称、标准开局也左右对称，所以 **红走 炮二平五 与 炮八平五 在棋理上完全等价**，
黑方的正确应手互为镜像。库因此**只写右手的线**，查表时先把局面做一次左右镜像归一：

- 两个互为镜像的局面落到**同一个键**上（`openingCanonicalFen()`：自身与镜像，取 FEN 小的当代表）；
- 命中镜像键时，候选着法**镜像回来**再返回（`mirrorMove()`）—— 上层拿到的永远是
  **当前局面下、能直接走的**着法。

于是「7 条线」覆盖的是**每一种形状**，而不是「从右边出子的那些走法」：
你走 炮八平五，AI 一样按谱走屏风马（镜像过来是 `马2进3`），不会掉进搜索里。

> **唯一成立的对称只有左右这一个。** 上下不对称（兵只能向前、将帅各在底线），
> 红黑不对称（同一种棋子两方的行进方向相反）—— 这两种「归一」都是错的，别照着抄。
> 镜像映射与着法镜像都在 [`js/position.js`](../js/position.js) 的
> `mirrorIdx` / `mirrorMove` / `mirrorPosition`。

## 3. 索引怎么建：局面 → 候选着法（带权重）

加载时把每条线从 `START_FEN` **逐步走一遍**，把「走这一步**之前**的局面」当键记下来：

```
局面（规范化 FEN + 左右镜像归一，含轮走方）  →  [ { move, weight }, ... ]
```

四件事：

1. **键是规范化后的完整 FEN** —— 用 `toFen(parseFen(fen))`，所以尾部字段写成
   `w - - 12 34` 的同一个局面也能命中。
2. **轮走方必须在键里** —— 同一个盘面轮到谁走，可选着法完全不同。
3. **不同线走到同一个局面时会自然合并**（真正的转置）。比如屏风马与顺炮都从
   `炮二平五` 起步，于是「第 1 手之后」这个局面下，黑方的候选里**同时**有
   `马8进7` 和 `炮8平5`，权重分别是 3 和 2。
4. **左右镜像归一**：局面自身与它的镜像，取 FEN 小的那个当代表，于是 `炮二平五` 之后
   与 `炮八平五` 之后是**同一个键**（见上一节）。建索引时把着法换成代表朝向的写法存，
   查表命中镜像键时再镜像回来 —— **建与查必须用同一个规则**，否则「存的」和「取的」对不上。

> **这里和 `solution-book.js` 的取舍正好相反，值得说清楚。**
> 那边存的是「一条**线**」，同一个局面在**不同线上要走向不同的着法**（杀线里重复局面
> 是常态），所以必须**按着法序列逐手比前缀**，只用局面当键会互相覆盖。
> 而开局库的候选**只取决于局面**（转置后着法一样成立），所以按局面查表才是对的。
> **「同名局面要不要当同一个东西」，取决于这个数据有没有「路径依赖」。**

## 4. 引擎怎么用它

在 `engine.js` 的 `search()` **最开头**（连 `Searcher` 都不必构造）：

```js
if (lv.book > 0 && rng() < lv.book) {
  const bookMove = pickOpening(fen, rng);
  if (bookMove && generateLegalMoves(pos).includes(bookMove)) {
    return { move: bookMove, …, depth: 0, nodes: 0, book: true };
  }
}
```

四个刻意的选择：

| 选择 | 为什么 |
|------|--------|
| **走谱时不搜索** | 开局库的意义就是「这一步不用算」。返回的 `depth` / `nodes` 都是 0、耗时 0ms —— 对「实时 AI」天然友好 |
| **走谱时不施加挡位弱化** | 谱上的着法是「已知合理的开局」，不是搜索结论。把它换成随机着法（`blunderRate`）坏掉的不是棋力，是**「像不像人」**本身 |
| **返回前再过一遍 `generateLegalMoves`** | 数据写错、或者局面其实不是库里那一个时，宁可回退常规搜索。**绝不能把非法着法交给上层** —— 上层会静默丢掉它，表现成「AI 不动了」（`future-work.md` E9） |
| **谱外一律回退搜索** | 对手不按谱走、这一步走岔了、库没写到那么深 —— 行为与没有开局库时一模一样 |

### 和挡位的关系：`LEVELS[k].book` 是**查谱概率**

| 挡位 | `book` | 效果 |
|------|--------|------|
| 入门 | 0.5 | 一半的时候走谱，另一半走搜索（于是还有机会出现新手的失误） |
| 初级 | 0.7 | 多数时候走谱 |
| 中级 | 0.9 | 基本都走谱 |
| 高级 | 1 | 只要局面在库里就一定走谱 |

弱挡位给低值是有意的：**它们本来就该常常不按谱走、露出新手的样子**。
（这也符合本模块一直的做法 —— 弱化手段全部声明式地写在挡位表里，不散在 `if` 里。）

### 和「AI 按谱应着」不是一回事

界面上那个「AI 按谱应着」开关管的是**残局的解法线**（`solutions.js` / `prefixes.js`，
由 Pikafish 离线算出）。两者的区别：

| | 开局库（本文档） | 「AI 按谱应着」（残局解法） |
|---|---|---|
| 数据来源 | **手写**的常识 | **引擎生成**的杀线 |
| 生效范围 | 标准开局的头几手 | 残局库里有解法的那些局 |
| 默认 | **开着**（按挡位） | **关着**（要玩家自己打开） |
| 走岔之后 | 回退引擎搜索 | 回退引擎搜索 |

> 「AI 按谱应着」默认关，是因为**同一个挡位不该在有解法的局里换一种风格**（`decisions.md`
> 第 10 条附近的记录）。开局库不冲突：它对所有局面一视同仁地生效，是「挡位的一部分」，
> 不是「某个局面的特殊行为」。

## 5. 怎么加 / 改一条手写的线（`LINES`）

1. 在 `js/openings.js` 的 `LINES` 里加一行（或改一行）。
   `moves` 用 ICCS 写，红先、红黑交替。
   **不用为镜像再写一遍** —— 左右对称的那一半由归一自动覆盖，写两遍只会多维护一份权重。
2. **跑测试**：

   ```bash
   node chinese-chess/tools/test-openings.mjs
   ```

   它会**从标准开局逐步重放每条线**，每一步都断言：

   - 是当前局面的**合法着法**（记法算错、棋子不在那儿、蹩腿、塞眼都会在这里当场变红）
   - 走子方与手数一致（红先交替）
   - 这一步**确实出现在库对这个局面的候选里**（说明索引建对了）
   - 库里这个局面的**所有**候选（含转置合并进来的）都是合法着法
   - 索引里的局面数 = 所有线前缀局面的**归一键数**（不多不少）
   - **镜像**：左右镜像的局面也能命中，且镜像回来的候选在镜像局面里同样合法

   再跑一条自对弈，肉眼确认开局走得正常：

   ```bash
   node chinese-chess/tools/selfplay.mjs hard hard 20
   # 谱上的着法会标 [开局库]（深度 / 节点都是 0，这一点就是「它没搜」）
   ```

**手写着法最容易出的三种错都是静默的**：走不通、走子方写反、索引键算错。
所以上面那层逐步重放**不是走过场** —— 它是 `future-work.md` E10 那条教训的正面用法：
数据有外部标准（象棋规则）时，一定要有一层**自己写的校验**钉住，不能只靠「看起来对」。

## 6. 生成谱：怎么重跑、参数怎么调

生成的那半是**离线产物**，日常不用管；要改它，三条命令：

```bash
node chinese-chess/tools/gen-openings.mjs grow      # 长树（可分批：--budget-ms 毫秒）
node chinese-chess/tools/gen-openings.mjs report    # 只看覆盖与体积
node chinese-chess/tools/gen-openings.mjs emit      # 写成 js/openings-generated.js
```

中间结果在 `tmp/openings-work.json`（tmp 已被忽略），**可中断、可分批、可重跑**：
每个局面记一条「候选 + 分值」，重跑时算过的不会再算。当前那版的实测量级：

| 参数 | 值 |
|------|-----|
| 深度 | 8 个半回合（4 个回合） |
| 每层保留候选数 `K` | `6,5,4,3,2,2,2,2` |
| 每层分值阈值 | `50,45,40,30,25,25,20,20` cp |
| 每个局面让 Pikafish 搜多深 | 12 层（开局着法分差本来就只有几十 cp，够排序） |
| 线程 / 引擎 | 4 线程，Pikafish 2026-09-06 |
| 结果 | 1,789 个局面 / 3,492 条候选 / 185 KB（gzip 17 KB）/ **95 秒** |

**K 与阈值是两个不同的旋钮，别混**：

- **阈值**管**质量**（这个着法坏不坏）—— 放宽它，谱里会收进「人可能走、引擎认为不最优」的着法；
- **K** 管**数量**（每个局面最多给几个选择）—— 放宽它，AI 变着更多、对「对手走偏」更宽容。

两个都放，树按层数指数膨胀。所以默认**由宽到窄**：前几手宽（人类在这里变化最多），越深越窄。
权重由分值差现算（`0cp→4、12cp→2、25cp 以外→1`），改权重**不用重跑引擎** —— 工作文件里存的是 cp。

### 它治什么、不治什么（最容易误解的一条）

- **治**「开局不像人」：1,789 个局面比 7 条线宽两个数量级，深水区尤其明显
  （你走 `炮八平五`，AI 从谱上应 `马2进3`，而不是搜索临场想的对攻着法）。
- **不治**「对手走偏」：谱里只有引擎认为可走的着法。对手走一步次优着就掉出谱
  （例：`炮五进四` 比最优差 34cp，被 25cp 阈值挡在树外），AI 立刻回退搜索 ——
  而**搜索的强弱是另一条战线**（`docs/future-work.md` C1：先分清估值问题还是视野问题）。
  实测：给模块自己的引擎 60 秒（只到 depth 8），它仍然看不见那条线，要 depth 11~12 才够。
- 所以「加深谱」只是把露馅的时刻往后推，推不掉。真想提升棋力得动**评估**
  （棋力那条线在**评估**上，不在谱里 —— 不过「换成 Pikafish 拟合的位置表」
  2026-10-05 试过、没成，见 `future-work.md` C1）。

生成过程里有两件值得知道的事：

1. **整棵树在「归一朝向」里长**（与查表同一套规则），引擎调用与数据都省掉近一半 ——
   开局阶段左右对称的局面一大把（`炮二平五` / `炮八平五` 就是一对），它们是同一件事。
2. **4 线程下 Pikafish 的分值有微小抖动**，重跑同一局权重不一定逐位相同。
   要严格可复现就用 `--threads 1`（慢）；生成物一旦 emit 就固定了，抖动不影响线上。

## 7. 特意不做的事

| 不做 | 为什么 |
|------|--------|
| **追求开局理论的深度** | 库到第 4~8 手就停。再深要维护一整套变例树，体量是现在的几十倍 |
| **为左右两半各写一遍线** | 左右镜像的局面棋理等价，写两遍只是把同一份数据存两份（权重还要各自维护、迟早不一致）—— 查表时归一一次就够。**上下 / 红黑不能这么归一**（那两个方向不是对称） |
| **放进 `solutions.js` / `prefixes.js`** | 那两个是**离线引擎生成的产物**、针对残局；开局库是**手写常识**、针对标准开局。混在一起会让「谁是生成物」说不清，也会把 Worker 拖进几百 KB 的解法数据里 |
| **按局面哈希查表** | 用规范化 FEN 当键。哈希有碰撞，开局库是**数据**不是缓存，不值得为省几微秒冒改错着法的风险 |
| **对「中途换局」的用户局面生效** | 键是完整局面，所以只有真正走到库里那些局面才命中。分享链接 / 自定义局面里如果恰好走到某条线的局面，也会命中 —— 这是对的（转置本来就是按局面判的） |
| **从棋谱数据库生成** | 需要一份有授权的谱库、且要逐条核对（`future-work.md` B1 是同一个判断）。**生成谱的输入是引擎自己的搜索输出**，没有授权问题 —— 那是另一件事，见上一节 |
