## 1. 目标与非目标

### 1.1 目标

1. 浏览器中单机对弈中国象棋，纯静态 HTML + CSS + JS，无构建工具、无框架、无第三方依赖。
2. 规则完整：河界、九宫、炮隔子吃、马蹩腿、象塞眼、兵过河、将帅不可照面、困毙判负。
3. 四挡 AI（入门 / 初级 / 中级 / 高级），挡位参数集中为一张声明式策略表。
4. **双人对弈模式**：一个开关关掉 AI，红黑两边都由人来点（同一台设备上轮流走）。
5. 内置残局库（8 局实用残局 + 《适情雅趣》全谱 551 局），分「实用残局」与「适情雅趣」（排局谱）两类，支持训练。
6. 中文记谱（`炮二平五`）+ 着法列表 + 点任意一步回退到该局面。
7. 对局操作：悔棋 / 重开 / 翻转棋盘。
8. 提示：用当前挡位的 AI 给出建议着并高亮。复用 §7.4 的搜索通道，边际成本接近零（与 §1.3 的 FEN 同理）。
9. 深色模式跟随全站，无需额外适配代码。

### 1.2 非目标（明确不做）

| 不做 | 原因 |
|------|------|
| 联网对弈、账号、排行榜 | 本仓库是静态站点，没有后端 |
| 中国象棋的循环规则（长将 / 长捉 / 长兑判负） | 规则本身极其复杂，且与「重复局面」纠缠。见 §5.3，只做三次重复判和 |
| 开局库、残局表库 | 数据量与维护成本远超本次范围 |
| 让子 / 让先 | 未被要求 |
| 多局存档（存好几盘棋来回切） | 一个 localStorage 槽位只够「接着上次下」；多局要有列表 / 命名 / 切换一整套。想要的其实是「局面」而不是「棋局」，那用自定义局面就够（§1.3） |
| 局面编辑器（自由摆棋） | 未被要求；残局库用 FEN 描述即可 |
| 计时器 / 步时限制 | 未被要求 |
| 音效 | 未被要求 |

### 1.3 局面的进出：FEN、自定义局面、分享链接

**FEN 解析器是必需的基础设施** —— 残局库的数据格式就是 FEN。既然解析器一定存在，
把它暴露到界面上（粘贴导入 + 复制导出）的边际成本接近零，
而它正好解决了「从网上弄到的残局怎么进库」这个问题（残局数据在网上普遍是 FEN/EPD 纯文本）。

于是「局面怎么进来、怎么出去」一共四个方向：

| 方向 | 入口 | 用途 |
|------|------|------|
| **FEN 入库**（进） | 保存 / 导入 → 存为自定义局面 | 把框里那个局面收进库里，以后反复练 |
| **FEN 直接载入**（进，但不落库） | 保存 / 导入 → 载入到棋盘 | 只想摆上去看看 / 接着下，不想往库里塞 |
| **复制 FEN**（出） | 棋盘下方工具栏 | 把局面给到别的软件 / 棋谱 |
| **复制链接**（出） | 棋盘下方工具栏 | 把局面**给人看** —— 对方点开就是 |

两种「进」的输入是**同一个 FEN 框**，它打开时就填着当前局面 ——
所以「存当前这盘棋」不需要单独一个动作，不动它就是当前局面。
两种都落在 `custom-endgames.js` 的校验上，但**一种留下、一种不留**：
留下的是「自定义」分类里的一条，不留的只是一个**临时局面**（和分享链接打开的局面同类）。
后两者都是「把当前局面拿出去」，区别只在形式：FEN 要对方自己找地方粘，链接点开就是。

**分享链接只带局面，不带这盘棋。** 着法历史会让链接长到没法看，而挡位、执子方是
**接收方**的偏好，不该被分享者覆盖。所以链接的语义是「来看这个局面」，
不是「来看我下的这盘棋」。

**另有一个不走 FEN 的「出」：复制着法。** 上面四个方向拿出去的都是**局面**，
而棋谱（`1. 仕五退四 车7进4` 这样的文本）拿出去的是**过程** —— 它对应的入口
也就不是工具栏，而是「着法」面板自己：复制的是那个列表，按钮就长在列表旁边。
复制的是列表里**全部**着法（和屏幕上显示的一致），不做列对齐（汉字与数字混排对不齐）。

**进来但不落库的那种局面叫「临时局面」**（代码里叫自由局面）：分享链接打开的是它，
「载入到棋盘」摆上来的也是它。它**不进自定义库** —— 打开一个链接不该悄悄往别人的
自定义列表里塞东西（想留着的话，界面上本来就有「存为自定义局面」）。
代价是它不属于任何分类，所以界面靠 **「`endgameId` 为空 且 `initialFen` 不是标准开局」**
认出这种状态（`main.js` 的 `isFreePosition`），显示成「临时局面」。
不另存标志位是为了让**从存档恢复出来的也认得出来**，刷新前后表现一致。

链接的校验**比 `validateEndgameFen` 松**：那条路还要求「轮走方有合法着法」，
而分享是**对局中途**截出来的 —— 你刚把对方将死就复制了链接，
接收方打开就该看到那个局面。详见 `js/share.js` 的注释。

## 3. 架构决策

每条都记下**否决了什么**，避免以后重复讨论。

### 3.1 局面表示：一维 `Int8Array(90)`

| 方案 | 结论 |
|------|------|
| 对象棋子数组 | 否决。7 层搜索每次分配几十万对象，GC 压力大 |
| 位棋盘（BigInt / 双 45 位） | 否决。象棋不是 64 格，BigInt 在 JS 里慢，收益不成立 |
| **一维 `Int8Array(90)`** | 采用 |

理由不只是性能：局面因此成为一个**可以 90 字节廉价拷贝的值**，置换表、终局判定、存档全都变简单。棋盘只有 90 格，用二维数组换来的可读性抵不过每次搜索分配对象的代价。

**不加边界哨兵。** 象棋的着法约束（河界、九宫、蹩腿、塞眼）本来就得分棋子类型手写，边界检查只是其中一条；加哨兵省不了多少，反而引入「哨兵值不能干扰 `Math.sign()` 判色」这类需要时刻记住的约定。

### 3.2 渲染：DOM + CSS，不用 Canvas

这条**刻意反着 `conway-life-game` 的选择**，因为两个场景的需求正好相反：

- 颜色走 CSS 变量 → **深色模式自动生效，不需要监听 `themechange`**（conway 里「页面黑了、棋盘还白着」那个坑直接消失）
- 命中测试用事件委托，免费
- 90 格 + 32 子，DOM 性能完全够；格子用 `<button>`，键盘可操作
- 代价：棋子移动动画要用绝对定位 + `transform` 手写，略啰嗦。但比在 canvas 里自己实现主题、命中、无障碍三件事便宜

**棋子字形**：CSS 画圆 + 汉字，字体栈 `"KaiTi", "STKaiti", "SimSun", serif`。
缺楷体的系统（部分 Linux、部分 Android）会兜底成衬线体，改进路径见
[`future-work.md`](./future-work.md) C5。

### 3.3 AI：Worker + 迭代加深 alpha-beta，挡位是一张声明式策略表

- 搜索必须跑在 **Web Worker** 里，否则高挡位搜索 1.5 秒会把页面冻死、连「思考中」的动画都不转。
- 对外只有两个入口：`search(fen, level)` 与 `searchAsync(fen, level)`。引擎内部换算法不动接口。
- 挡位参数集中在 `config.js` 的 `LEVELS` 表，每个挡位是一组声明式参数，不是散在代码里的 `if`。

**关键设计点：低挡位关掉静态搜索（quiescence）。** 这是让 AI「像新手」最有效的单个开关——它会让 AI 在兑子序列中途停下、以为自己占便宜，结果被吃回。这恰恰是初学者的真实特征，比单纯降深度像得多。

### 3.4 撤销与复盘：着法列表里存 FEN 快照

初版设计想用「初始 FEN + 重放 N 步」，评估后改为**每步存一份 FEN 快照**：200 步 × 约 60 字符 ≈ 12KB，换来复盘跳转 O(1)。

`conway-life-game` 用快照式撤销是因为棋盘大（几十 KB 一份）；象棋的局面只有 90 字节，直接存文本 FEN 更省事，而且同一份数据同时供悔棋、复盘跳转、着法列表显示、FEN 导出使用。

## 4. 核心数据模型

### 4.1 坐标与编码

- 棋盘 9 列 × 10 行。`x` 向右为 0..8，`y` 向下为 0..9（与屏幕一致，也与 `conway-life-game` 的约定一致）。
- 下标 `idx = y * 9 + x`，范围 0..89。
- 黑方在 `y = 0..4`，红方在 `y = 5..9`；河界在 `y = 4` 与 `y = 5` 之间。
- 九宫：红方 `x ∈ [3,5], y ∈ [7,9]`；黑方 `x ∈ [3,5], y ∈ [0,2]`。

棋子编码（`Int8Array(90)` 的元素值）：

```js
const EMPTY = 0;
// 红方为正
const K = 1;  // 帅
const A = 2;  // 仕
const B = 3;  // 相
const N = 4;  // 马
const R = 5;  // 车
const C = 6;  // 炮
const P = 7;  // 兵
// 黑方为对应的负值：-K .. -P
```

判色用 `Math.sign(v)`，判类型用 `Math.abs(v)`。`EMPTY === 0` 且 `Math.sign(0) === 0`，所以「目标格为空或敌子」可以写成 `Math.sign(target) !== Math.sign(mover)`。

### 4.2 着法表示

着法编码为单个整数：`move = from * 90 + to`，范围 0..8099。

- 解出：`from = Math.floor(move / 90)`，`to = move % 90`
- 被吃子从局面上查（`position[to]`），不存进 move——保证 move 只是「从哪到哪」，不含冗余状态

选整数而不是对象，是为了让着法能直接当置换表的键和着法排序的数组元素，不用分配对象。

### 4.3 FEN 格式

采用象棋界主流格式（象棋巫师 / Pikafish 兼容）：

```
rnbakabnr/9/1c5c1/p1p1p1p1p/9/9/P1P1P1P1P/1C5C1/9/RNBAKABNR w - - 0 1
```

- 十行用 `/` 分隔，**第 1 行是黑方底线（`y = 0`），第 10 行是红方底线（`y = 9`）**，与 §4.1 的 y 方向一致
- 数字表示连续空格数
- 小写为黑、大写为红：`k/K` 将帅、`a/A` 士仕、`b/B` 象相、`n/N` 马、`r/R` 车、`c/C` 炮、`p/P` 卒兵
- 第 11 字段为轮走方：`w` 红、`b` 黑
- 后三个字段 `- - 0 1` 本模块不使用，解析时忽略、生成时固定输出该字面值

**不用 `h`（马）/ `e`（象）那套老式字母**——`rnbakabnr` 这套是主流工具链的通用格式，兼容性更好。

格式示例（一个合法的「车对双士」局面，用于说明格式，不是残局库内容）：

```
3aka3/9/9/9/9/9/9/9/9/R2K5 w - - 0 1
```

### 4.4 Zobrist 哈希

- 90 格 × 14 种棋子 = 1260 个随机数，外加 1 个「轮走方」随机数。
- 用 **32 位整数**（`Math.imul` 保持 32 位语义），不用 64 位。
- 碰撞概率：搜索节点数在 10^6 量级，`10^6 / 2^32 ≈ 0.02%`。置换表查找时**额外校验完整局面或着法**，所以碰撞只会导致缓存失效，不会产生错误着法。

## 5. 规则引擎（`rules.js`）

### 5.1 着法生成

分棋子类型手写，全部生成**伪合法着法**（不检查走完后自己是否被将军）：

| 棋子 | 规则要点 |
|------|----------|
| 车 `R` | 四方向直线滑动，遇子停止，遇敌子可吃 |
| 炮 `C` | 四方向直线：**无隔子时只能走空格**；**恰好隔一个子时可吃该子后的第一个敌子**；隔两个及以上不可 |
| 马 `N` | 八个日字目标；**马腿**为「先直走的那一格」，该格有子则此方向全部禁止 |
| 象 `B` | 四个田字目标；**象眼**为田字中心，有子则禁；不得过河（红方 `y ≥ 5`，黑方 `y ≤ 4`） |
| 士 `A` | 四个斜向一格；不得出九宫 |
| 将 `K` | 四方向一格；不得出九宫 |
| 兵 `P` | 未过河只能向前一格；过河后可向前或左右一格；**永不后退**（红方「前」为 `y` 减小） |

### 5.2 合法性

伪合法着法 → 试走 → 检查己方将是否处于被攻击状态 → 非法则回退。

「被攻击」的检查包含**将帅照面**（同一纵线上无子相隔即视为互相攻击）。用试走 + 回退而不是「生成时过滤」，是因为前者只有一处判断逻辑，不容易漏。

### 5.3 终局判定

| 情况 | 判定 |
|------|------|
| 一方无任何合法着法，且其将被攻击 | 将死，该方负 |
| 一方无任何合法着法，且其将未被攻击 | **困毙，该方负**（中国象棋与国际象棋不同，困毙是负不是和） |
| 同一局面出现三次 | 判和 |

**循环规则不做**（长将 / 长捉 / 长兑 / 一将一杀判负）。这是本次最重要的范围裁剪：中国象棋的循环规则需要记录每一步的「捉」「将」意图并比较循环内的行为，实现复杂度和测试成本都极高，而它只在极少数残局里才影响胜负。只做三次重复判和，足以避免无限循环。

### 5.4 局面合法性校验（供残局库使用）

`isLegalPosition(pos)` 检查：

1. 双方各恰好一个将 / 帅
2. 将帅不照面
3. 所有棋子都在自己的合法区域内（士 / 象 / 兵的位置约束）
4. 兵 / 卒不在己方底线（红兵 `y ≠ 9`，黑卒 `y ≠ 0`）
5. 非轮走方不处于被将军状态（即上一步不该让己方被将军）
6. 双方子力数量不超过理论上限（车 ≤ 2、马 ≤ 2、炮 ≤ 2、象 ≤ 2、士 ≤ 2、兵 ≤ 5）

## 6. 中文记谱（`notation.js`）

### 6.1 规则

格式：`棋子名 + 起始纵线 + 动作 + 目标`

- **纵线编号**：**红黑各自从自己的右手边数起**——两人面对面坐着，所以两方是**镜像**的：
  红方（在 `y = 9` 一侧，右手边是 `x = 8`）用汉字，`line = 9 - x`；黑方（在 `y = 0` 一侧，右手边是 `x = 0`）用阿拉伯数字，`line = x + 1`（1~9）。
  同一纵线上红「一」与黑「9」同列（`x = 8`），红「九」与黑「1」同列（`x = 0`）。
- **这条规则修正过一次**（初稿写的是「两方数值相同，都用 `9 - x`」，是错的）。当时实现、单测、界面全都照它执行——**内部完全自洽，所以一直没暴露**；是拿《适情雅趣》第 002 局的谱载解法去对（黑士 `(4,1)→(3,0)` 谱作「士5退4」，共用公式写成「士5退6」）才发现黑方整条方向是反的。教训见 `future-work.md` E10：**规则本身错了的时候，自洽的测试发现不了，得有外部基准钉住。**
- **动作**：`进` / `退` / `平`。红方「进」为 `y` 减小，黑方「进」为 `y` 增大。
- **目标**：`平` 记目标纵线；`进` / `退` 时，车 / 炮 / 兵 / 将记**步数**，马 / 象 / 士记**目标纵线**。
- **同纵线重子**：同一纵线上有两个同类棋子时，用「前」「后」替代起始纵线，如 `前车进三`。三个及以上（只可能是兵）用「前 / 中 / 后」，五个兵用「一二三四五」。

### 6.2 示例

| 局面 | 着法 | 记谱 |
|------|------|------|
| 红车在 `(0,9)` | 走到 `(0,8)` | `车九进一` |
| 红炮在 `(1,7)` | 走到 `(4,7)` | `炮八平五` |
| 黑马在 `(7,0)` | 走到 `(6,2)` | `马8进7` |
| 黑士在 `(4,1)` | 走到 `(3,0)` | `士5退4` |
| 黑马在 `(0,2)` | 走到 `(1,0)` | `马1退2` |

后两行不是随手编的，是**外部谱例锚定**：《适情雅趣》第 002 局「马蹀阏氏」的谱载解法，
也已和 Pikafish 算出的 PV 逐手对上。`test-notation.mjs` 里同样留了这两条（外加两条红方的）——
因为「规则本身写错」这种情况，只靠实现自证的用例是抓不到的。

### 6.3 实现要点

记谱生成需要当前局面（判断是否有重子、决定用纵线还是前后）。所以接口是 `toNotation(position, move) -> string`，而不是只看 move。

**只做生成，不做解析。** 复盘靠着法列表的索引，不需要从记谱串反推着法。

## 7. AI 引擎（`engine.js`）

### 7.1 搜索

- **负极大值（negamax）形式的 alpha-beta**
- **迭代加深**：从深度 1 逐层加深，每层结束记录最佳着法；`timeLimitMs` 用尽则停止。这样时间控制天然生效，且浅层结果可作深层着法排序的种子
- **置换表**：`Map<zobrist, { depth, score, flag, move }>`，`flag` 为 EXACT / LOWER / UPPER。查找时校验着法合法性（见 §4.4）
- **着法排序**（按优先级）：置换表着法 → 吃子按 MVV-LVA → 杀手着法（每层两个）→ 历史启发
- **根节点将军优先**：根着法里「走完之后对方被将军」的那些排在最前面。连杀的首着本身就是将军，它一旦被搜到，alpha 立刻升到杀棋分值，后面几十个着法会在很浅的地方就剪掉
- **将军延伸**：被将军的节点不消耗深度，一条线最多多搜 `checkExtension` 层。被将军时合法着法通常只有一两个，很便宜；而强制手段是一整条将军
- **连将杀探测**：常规搜索之前先做一次「**攻击方只走将军着法**」的强制杀搜索，见下面的说明
- **不实现**：空着裁剪、后期着法减少、吃子延伸

**超时用抛异常中断，所以 searcher 的棋盘必须能回滚**（`Searcher.guarded`）。异常会从
`make()` / `unmake()` 中间穿过去，棋盘停在「走了一半」的状态上，而调用方之后还要用它生成
根着法（挡位弱化）—— 不还原就会从错乱的棋盘上挑出非法着法，上层拒掉它，表现成「AI 不动了」。

**为什么必须有连将杀探测（`Searcher.probeMate`）。** 只加将军延伸仍然不够：同一个局面
（《适情雅趣》第001局「气吞关右」，13 层连杀）在「高级」挡位下要**上千万节点、11 秒**才看得见，
超出 1.5 秒的预算。瓶颈在攻击方的节点上 —— 常规搜索要把约 40 个着法全部摊开，而连杀的正解
**整条都是将军**。把攻击方限制在将军着法上，同一条杀棋降到 196k 节点 / 0.75 秒。

它**只证明「有杀」、不证明「没有杀」**：攻击方的着法被限制过，找不到不等于没有（正解里可能有
一步闲着）。这个方向恰好是安全的 —— 找到的杀一定是真杀，可以直接走；找不到就退回常规搜索，
什么也没损失。所以它是**前置探测**，不是常规搜索的替代品。

成本用两道闸封住：`mateProbePly`（层数上限）和总预算的一部分（`MATE_PROBE_SHARE` /
`MATE_PROBE_MAX_MS`）。没有将军着法的局面是 0 个节点；随机中局实测 0~2ms；最坏就是上面那局。

**探测到杀棋时不施加挡位弱化**（见 §7.3）：杀棋是证明，不是评估。把已经证明的杀棋换成随手
一步，坏掉的不是棋力而是可信度 —— 残局库的「提示」会给出错的答案。

### 7.2 评估函数

第一版**刻意简化**，只做子力 + 少量结构项，不做 90 格位置表：

| 项 | 分值 |
|----|------|
| 车 | 900 |
| 炮 | 450 |
| 马 | 400 |
| 士 | 200 |
| 象 | 200 |
| 兵（未过河） | 100 |
| 兵（过河） | 150 |

评估是独立函数 `evaluate(position, sideToMove) -> number`，返回轮走方视角的分值。**替换成完整的位置表版本时只需改这个函数**——这是「方便后续优化」的具体落点。

**刻意不加机动性项。** 评估在叶节点被调用上百万次，而「机动性 = 合法着法数」需要为每一方生成全部着法，等于把搜索成本翻倍。子力 + 兵过河虽然弱，但成本只是 O(32) 的数组遍历。想提升棋力，正确的下一步是加 90 格位置表（同样是 O(1) 查表），而不是加任何需要生成着法的项。

### 7.3 挡位表（`config.js` 的 `LEVELS`）

四个挡位，不是五个：深度 6 与 7 对普通玩家体感没有差别，耗时却翻倍。

| id | 名称 | depth | timeLimitMs | quiescence | noise | blunderRate | checkExtension | mateProbePly |
|----|------|-------|-------------|------------|-------|-------------|----------------|--------------|
| `novice` | 入门 | 1 | 200 | 关 | 120 | 0.35 | 0 | 0 |
| `easy` | 初级 | 3 | 400 | 关 | 60 | 0.15 | 0 | 0 |
| `medium` | 中级 | 5 | 1200 | 开 | 20 | 0.03 | 6 | 13 |
| `hard` | 高级 | 64 | 1500 | 开 | 0 | 0 | 6 | 15 |

- `depth` 是迭代加深的上限，实际由 `timeLimitMs` 截断
- `noise`：给根节点每个着法的评分加一个 `[-noise, +noise]` 的均匀随机扰动，单位与评估函数相同。让弱挡位倾向选次优着而不是永远选最优
- `blunderRate`：以该概率放弃搜索结果，改为「从合法着法中**排除掉最优着法后**随机选一个」——模拟看漏。**只剩一个合法着法时不触发**（否则会走出非法着法）。**探测到连杀时也不触发**（见 §7.1）
- `checkExtension`：将军延伸的层数上限，0 = 不延伸。弱挡位给 0 —— 新手本来就该看不清强制手段
- `mateProbePly`：连将杀探测的层数上限，0 = 不探测。弱挡位给 0，道理同上

`medium` 的时间上限从 800 提到 1200 只是给探测留的：它的常规搜索本来就被 `depth 5` 卡住
（几百毫秒就返回），多出来的预算只有探测会用。`hard` 没动，所以「一步最多等 1.5 秒」仍然成立。

### 7.4 Worker 协议（`worker.js`）

单 Worker，`type: "module"`。搜索期间主线程禁用操作，不做中途取消（上限 1.5 秒，可接受）。

```js
// 主线程 → Worker
{ type: 'search', id: number, fen: string, level: string }

// Worker → 主线程
{ type: 'result', id: number, move: { from, to } | null,
  score: number, depth: number, nodes: number, timeMs: number, blundered: boolean }
{ type: 'error',  id: number, message: string }
```

`move` 为 `null` 表示局面已经终局、无着法可走。

**Worker 不返回 `notation`**：主线程在把着法记进对局状态时**本来就要调一次 `toNotation`**——玩家自己走的棋也要记谱——Worker 再算一遍是重复劳动，还让 Worker 多依赖一个模块。

Worker 只依赖 `engine.js`（以及它间接依赖的 `config.js` / `position.js` / `rules.js`）——这几个模块**不得 import 任何 DOM 相关模块**，否则 Worker 里会崩。`worker.js` 是本模块唯一允许碰 `self` / `postMessage` 的文件。

## 8. 残局库（`endgames.js`）

### 8.1 数据结构

```js
{
  id: 'che-vs-shuang-shi',        // 唯一标识，kebab-case
  name: '单车例胜双士',
  category: 'practical',          // practical 实用残局 | composed 适情雅趣
  fen: '3aka3/9/9/9/9/9/9/9/9/R2K5 w - - 0 1',
  result: 'win',                  // 先手方视角：win 胜 | draw 和
  difficulty: 2,                  // 1~5，训练难度
  source: '《象棋残局基础》',       // 来源，必填
  note: '车方需先逼将离位，再破士',  // 可选，一句话要点
}
```

`result` **只有 `win` 和 `draw`**，没有 `lose`——残局库里的局面都应当是先手方不劣的，否则没有训练价值。`verify-endgames.mjs` 会校验这一点。

**「适情雅趣」那一页不全是胜局。** 谱里 469 局往后夹了一批**和局**研究，局名里直接写着结论
（形如「第469局 单马独还（马双兵和双卒双士）」），这些局标 `draw` 而不是 `win` ——
整页套一个「红先胜」会把 51 局的事实写反。判定就是看局名里有没有「和」字，
判定结果**写进每一行数据**（`COMPOSED_RAW` 的第 4 项），不是取值时用正则跑一遍：
这样肉眼能核对，也不会因为改个正则就悄悄把一大片结果翻过来。

### 8.2 规模与来源

**分两类：**

| 分类 | 规模 | 定位 |
|------|------|------|
| **实用残局** `practical` | 8 局 | 教材定式（单车例胜单士 / 单象 / 双士 / 马双士、单车难胜士象全、双车必胜士象全、马擒单士、单马必胜单将…）。结果可靠，**是训练的主体** |
| **适情雅趣** `composed` | 551 局 | 《适情雅趣》全谱，一条不漏、FEN 一字未改。胜局与和局都有，多为十几步的连杀，适合欣赏，对入门偏难 |

> 初稿写的是「20~30 局」，只打算挑十几局排局当样例；后来直接收了全谱。数据量大了一个数量级，
> 但**成本几乎没变** —— 一次性的离线整理，运行时还是纯本地一张数组。

实用残局由本模块自己构造（红帅 `(3,9)` / 黑将 `(4,0)` 这类骨架），结果取自教材定式。
**但自己搭的骨架会改变结论**：`dan-ma-vs-dan-jiang` 最初按「单马难胜单将」标成和棋，
而这套骨架本身恰好是红方两步困毙（黑方被照面切掉一路，只剩一个落点）。
构造出来的局面要单独核实一遍，不能只把教材结论抄过来。

**数据来源（实际采用）：**

| 来源 | 内容 | 授权 |
|------|------|------|
| `github.com/kuiba1949/xiangqi-tools` 的 `fen/shiqingyaqu551.fen` | 《适情雅趣》551 局的 FEN 数据 | 仓库 BSD-3-Clause；《适情雅趣》为明代排局谱，公有领域 |

原文件每行形如 `[FEN_INDEX "shiqingyaqu-551-001"] [EVENT "...第001局 气吞关右"] [FEN "..."]`，
`FEN_INDEX` 用作 id、`EVENT` 里的局号局名用作 name。
**FEN 原样照抄，一个字符都没改**；id 与局名有**三处**人工整理：去掉局名里标记补图 / 异文的 `*`；
唯一一条没有局号的记录（`shiqingyaqu-551-228plus`）改成 id `shiqingyaqu-551-227` +
局名「第227局 舍生取义（补图复原）」；第 543 局局名括号前补了个空格。
逐条说明在 `js/endgames.js` 里 `COMPOSED_RAW` 上面那段注释。

**运行时绝不联网。** 流程是离线一次性把 FEN 整理进 `endgames.js`，之后纯本地——这符合本仓库
「纯静态、无外部请求」的约定，也避免 CORS 问题。

> 为什么没有收录「七星聚会」等江湖四大名局、另外两个备选来源为什么没用上 ——
> 见 [`future-work.md`](./future-work.md) B1。

### 8.3 校验（`tools/verify-endgames.mjs`）

逐局检查：

1. FEN 能被解析，且解析后重新生成与原文一致（往返一致）
2. `isLegalPosition()` 通过（§5.4 全部 6 条）
3. **该局面不是已经终局的**（轮走方有合法着法）
4. `result` 与 `category` 是枚举内的值，`difficulty` 在 1~5
5. `id` 全局唯一，`name` 与 `source` 非空
6. **子力一致性**：`result` 为 `win` 时，先手方的子力价值不应低于对手 —— 挡住「把强弱写反了」这类录入错误
7. **`result` 与实际胜负的吻合度：不做自动校验** —— 理由见下

**没有「轮走方不该已经被将军」这一条。** 那是合法局面（他应将就是了），
第 511 局的题面就是红方被将军。真正非法的只有「非轮走方被将军」，第 2 条里查了。

**第 6 条只对实用残局查。** 排局恰恰以「红方子力更少、靠连杀取胜」为常态，对它们套用这条规则
会大面积误报（实测 15 局里误报 12 局）。

**第 7 条是刻意留白的。** 要证明「红先必胜」需要可靠的求解器或权威棋谱，本模块的引擎
（简化评估 + 迭代加深）做不到。所以每局必须标 `source`，结论由用户实战验证 ——
详见 [`future-work.md`](./future-work.md) B6。

**这个脚本不是走过场** —— 它在实际开发时抓出过一局 FEN 把「将」和「士」的位置写反了。
案例见 [`future-work.md`](./future-work.md) E6。

### 8.4 自定义局面（`custom-endgames.js`）

静态库是「题库」，自定义局面是「我的局面」。两者除了查询入口共用，别的地方完全不同：

| | 静态库 | 自定义库 |
|---|---|---|
| 形态 | 代码里的常量 | localStorage 里的用户数据 |
| 谁维护 | 手工（本模块唯一维护点） | 用户自己增删改 |
| 结论 `result` | 有（先手胜 / 和） | **恒为 `null`** |
| 校验时机 | 开发期跑 `verify-endgames.mjs` | 入库时跑 `validateEndgameFen` |

**`result` 恒为 `null`。** 用户存的是对局中途的局面，程序无从知道胜负。
硬给一个「先手胜」就是在编造事实，而且会和静态库那批本来就「逐局未复核」的结论混在一起，
让人以为它是可信的。所以界面显示「自定义局面」、不做「达成目标」判定。

**FEN 校验分两层**（都在 `custom-endgames.js`，失败一律带原因给用户看）：

| 查什么 | `validateFreeFen`（载入到棋盘） | `validateEndgameFen`（存为自定义局面） |
|---|---|---|
| FEN 能解析 | 要 | 要 |
| `isLegalPosition()` 的全部 6 条 | 要 | 要 |
| 轮走方有合法着法 | **不查** —— 摆上去看看完全合理 | **要** —— 已经终局的局面没有练习价值 |
| FEN 规范化（尾部统一成 `- - 0 1`） | 要 | 要 |
| 名字非空 / 不超长 / 不与已存的重复 | 不适用（不落库） | 要 |

后一层就是前一层加一条，**别让两条路的准入悄悄分家** ——
「相同的那几条」在 `test-custom-endgames.mjs` 里是逐条对照着钉的。

> **「轮走方已经被将军」两层都不管。** 那是合法局面（他应将就是了），
> 而「我正被将、该怎么解」是正当需求 —— 摆得上去，也存得下来。
> 真正非法的「非轮走方被将军」在 `isLegalPosition` 里。

**三个写操作。** `addCustom`（新增；查重查的是 **FEN** 不是名字）、
`renameCustom`（**只改 `name`**，FEN 一个字符不碰）、`removeCustom`（删）。
前两个返回带原因的结果，`removeCustom` 只返回布尔 —— 它只有一个失败原因：id 不在。

**存储策略：逐条校验，坏的那条丢掉、好的留下。**
这和 `persist.js` 的「整份丢弃」**正好相反**，因为语义不同 ——
那边是「一个对局」（半份对局比没有更难查），这边是「一个列表」（丢一条好过丢全部）。

**合并方式：注册表。** `endgames.js` 里有一个 `setCustomEndgames()`，
`main.js` 启动时把从 localStorage 读出来的列表灌进去（**必须在恢复存档之前**，
否则恢复出来的 `endgameId` 可能指向一个还查不到的自定义局面）。

这样 `findEndgame` / `endgamesByCategory` 这两个**共用查询入口**能同时看到两个库，
而 `game.js` 的 `startEndgame` / `endgameOf`、`persist.js` 的存档格式
**完全不需要知道有「自定义」这回事** —— 这是整个设计里最省事的一处。

### 8.5 分享链接与自由局面（`share.js`）

链接格式只有一个参数：`?fen=<encodeURIComponent(FEN)>`。

**只带局面，不带这盘棋。** 着法历史会让链接长到没法看，而挡位、执子方是**接收方**的
偏好，不该被分享者覆盖。所以链接的语义是「来看这个局面」，不是「来看我下的这盘棋」。

**空格编成 `%20`，不用 `URLSearchParams`。** 后者会把空格编成 `+`，
而 `+` 在查询串里是否等于空格**取决于解析方** —— HTML 表单场景下是，别的地方不一定。
FEN 里有 5 个空格，一旦有一处把 `+` 当字面量，整条 FEN 就废了。
读回来那边不用改：`searchParams.get` 对两种编码都能正确解码。

**校验比 `validateEndgameFen` 松**，只查 `parseFen` + `isLegalPosition`：

| 查什么 | 出题（自定义局面） | 分享 |
|--------|-------------------|------|
| FEN 能解析、局面合法 | 要 | 要 |
| 不是已经终局 | **要** —— 没有练习价值 | **不查** —— 分享是**对局中途**截出来的，你刚把对方将死，对方打开就该看到那个局面 |

这条不一致是**故意**的，所以 `test-share.mjs` 里两边都断言了一遍 ——
否则很容易被后来的人当成 bug 顺手「统一」掉。
（「轮走方被将军」两侧都接受，也在那里钉着。）

**载入后是一个「临时局面」。** 分享来的局面**不进残局库**（打开一个链接不该悄悄往
别人的自定义列表里塞东西；想留着就用「存为自定义局面」）。于是它既没有 `endgameId`、
起始局面又不是 `START_FEN` —— 界面靠这两个条件认出它（`main.js` 的 `isFreePosition`），
显示成「临时局面」，并给一行「退出，回到标准开局」。

**这个状态还有一个来源**：「保存 / 导入」里把 FEN 框换成别处的局面、点「载入到棋盘」（`main.js` 的 `loadFen`，
走 `G.startPosition`）。两条路产出的是同一种东西，所以共用 `isFreePosition` 这一个判据 ——
界面不必知道局面是从链接来的还是从粘贴框来的。

不另存标志位是为了让**从存档恢复出来的也认得出来**：状态只有一个来源
（`game.initialFen`），刷新前后表现一致。

**参数读完立刻用 `history.replaceState` 抹掉。** 留着的话，之后每一次刷新都会把用户
从「他自己后来选的局面」拽回分享的局面 —— 那看起来很像 bug。
局面本身马上进存档，刷新照样恢复得回来。**参数无论好坏都抹掉**，
否则一个坏链接会每次刷新都报一次错。

### 8.6 解法（`solutions.js`）—— 生成物，不是手写数据

残局库原本只有题面与结论、没有解法（`future-work.md` C8 挂了很久）。现在按
**「离线生成 + 校验后固化」**补上：用 Pikafish（外部 UCI 引擎）对每局跑 `go mate`，
把**引擎证明了有杀**的主变（PV）存进 `js/solutions.js`。运行时照样零依赖、不联网。

| | |
|---|---|
| 数据形态 | `{ pv, mate, ms }`。`pv` 是用 **ICCS 坐标**（列 a-i 从左到右、行 0-9 从红方底线往上）写的着法序列 —— 与本项目内部编码无关，可以直接拿引擎或别的工具复核；`mate` 是杀棋步数（红方步数），所以 `pv` 长度应为 `2 * mate - 1` 个半层 |
| 生成 | `tools/gen-solutions.mjs`：`fast`（短预算）→ `slow`（对没解出的长预算，mate 上限封到 40 步）→ `emit`。中间结果落在被忽略的 `tmp/` 里，**可中断、可分批、可重跑** |
| 校验 | `tools/verify-solutions.mjs`：逐步合法 + 末局对方一步都走不出 + 长度与 `mate` 对得上 |
| 覆盖 | **只放证明了强制杀的局**。和局（谱载 `draw`）本来就没有「正解着一说」；没找到杀的局也不编 —— 界面上显示「暂无谱载解法」并回退到引擎搜索 |

**为什么自己跑引擎、而不是抄现成棋谱。** 网上流传的《适情雅趣》PGN 授权不明、链接易失效，
而且那份解法本身就是老引擎（EleEye / sjaakii）跑出来的。自己跑有三个好处：
授权干净（只运行、不分发）、可复现（换引擎版本重跑即可）、而且**顺带把 B6
（551 局胜负结论未经机器验证）一起收了** —— 生成过程会撞出「谱载胜、引擎却判定红方被杀」
这类矛盾局，单列成疑点清单交人工核查，而不是悄悄混进数据里。

**外部工具的产出，必须用自己的一层去钉。** 生成（Pikafish）与校验（我们的 `rules.js` +
`notation.js`）刻意是两套东西：坐标换算方向、局面是不是同一个、杀棋是不是真杀，
三件事都在校验里钉死。这是 E10 那条教训的正面用法 —— 也是「复制着法」当天抓出记谱
方向错误的同一条思路。

**授权**：Pikafish 是 GPL-3，NNUE 权重来自 Pika Xiangqi Zero（ODbL）。我们只**离线运行**
它、只取输出（着法不是版权客体），可执行文件与权重**不进仓库**（放在被忽略的 `tmp/` 下），
`tools/` 里只有自己写的驱动脚本，README 写明要自行下载。运行时不需要引擎 ——
数据一次性固化，与 FEN 同源同法。

## 9. 对局状态机（`game.js`）

### 9.1 状态

```js
{
  initialFen: string,           // 起始局面（残局模式下是残局库的 FEN）
  moves: [{                     // 着法列表
    move: number,               // 整数编码
    notation: string,           // 中文记谱
    captured: number,           // 被吃子的编码（0 表示没吃）
    fenAfter: string,           // 走完后的 FEN 快照
  }],
  cursor: number,               // 当前处在第几步（0 = 起始局面）
  mode: 'play' | 'endgame',
  endgameId: string | null,     // 残局模式下是哪一局
  playerSide: 1 | -1,           // 与全模块一致，用符号判色（§4.1），不用 'w' / 'b'
  level: string,
  twoPlayer: boolean,           // 双人对弈：不派发 AI 搜索，两边都由人点
}
```

**`twoPlayer` 只影响三处行为**（其余逻辑一律不知道它存在）：

| 位置 | 人机模式 | 双人模式 |
|------|----------|----------|
| 谁来派发搜索（`main.js` 的 `requestAiMove`） | 轮到非玩家方时派发 | **永不派发** |
| 能不能点棋盘（`main.js` 的 `canAct`） | 只在玩家的回合 | **任何回合都能点** |
| 悔棋退几步（`game.js` 的 `undoToPlayer`） | 退到「轮到玩家走」为止 | **只退一步** |

最后一条最容易被忽略：人机模式要多退一步是因为「只退一步的话 AI 立刻又走一步，
体验上等于悔棋没生效」；双人模式没有这个前提，多退一步反而把对手刚走的那手也抹掉了。

**开着的时候 `playerSide` 只剩「初始是否翻转棋盘」这一个作用**，
所以界面会把「执子」禁掉 —— 留着可点会让人以为它还有别的效果。


**终局状态不存进 state。** 它是每次需要时由 `evaluateStatus(game)` 现算的
（返回 `{ type, winner }`，`type` 为 `playing` / `checkmate` / `stalemate` / `repetition`）。
存进 state 就要在走子、悔棋、复盘跳转三处同步维护，而那正是 §9.3 想避免的「两份真相」。
现算的成本是一次着法生成，界面上完全可以接受。

### 9.2 操作

| 操作 | 实现 |
|------|------|
| 走子 | 校验合法性 → push 到 `moves` → `cursor++` → 触发渲染 → 若轮到 AI 则派发搜索 |
| 悔棋 | `cursor--`，若回退后轮到 AI 再退一步（保证回到玩家走棋）。**不删 `moves`**，只移动游标 |
| 复盘跳转 | 直接 `cursor = N`，取 `moves[N-1].fenAfter`（O(1)，见 §3.4） |
| 在回看状态下走新着法 | 截断 `moves` 到 `cursor` 再 push，重做链作废 |
| 重新开始 | 清空 `moves`，`cursor = 0`，回到 `initialFen` |

### 9.3 当前局面

`currentPosition()` = `cursor === 0 ? parseFen(initialFen) : parseFen(moves[cursor-1].fenAfter)`。

**局面只有一个来源**：FEN 字符串。内存里不额外维护一份 `Int8Array` 作为「真相」——每次需要时从当前 FEN 解析（90 格解析是微秒级），这样复盘跳转、悔棋、走子全都走同一条路径，不可能出现「状态不同步」。

## 10. 界面

### 10.1 布局

```
┌──────────────────────────────────────────────────┐
│ ← 返回首页                                        │
│ 中国象棋  [局面库 · 标准开局 ▾]  [保存 / 导入]     │
│ 单机对弈 · 四个挡位 · 中文记谱与复盘（可折叠说明）│
├────────────────────────────┬─────────────────────┤
│                            │  对局面板            │
│         棋盘                │  挡位 / 执子 /      │
│                            │  双人对弈开关 / 状态 │
│       （9×10 格）           ├─────────────────────┤
│                            │  着法列表            │
│                            │  （可点击跳转）      │
│                            │                      │
│                            │  ↑ 与棋盘等高，      │
│                            │    正好收在棋盘下沿  │
├────────────────────────────┴─────────────────────┤
│ 悔棋 / 重做 / 重开 / 翻转 / 提示 / 复制 FEN / 复制链接│
└──────────────────────────────────────────────────┘
```

**桌面布局用显式网格定位**（`grid-area`），不是靠 DOM 顺序：

| 位置 | 内容 |
|------|------|
| 第 1 行第 1 列 | 棋盘 |
| 第 1 行第 2 列 | 侧栏（对局面板 + 着法面板） |
| 第 2 行第 1 列 | 工具栏 |

**工具栏必须独立成一行**，不能塞回棋盘列里 —— 否则第 1 行的高度会变成「棋盘 + 工具栏」，
侧栏跟着变高，着法列表就伸到棋盘下沿之外了。这样摆之后第 1 行两列等高，
侧栏里的着法面板用 `flex: 1` 吃掉对局面板剩下的全部高度，
列表于是**正好收在棋盘下沿**（实测差值为 0）。

**移动端**（`max-width: 860px`）：改回单列，`grid-area: auto` 让顺序回到 DOM 顺序
（棋盘 → 工具栏 → 侧栏）。此时侧栏高度由内容决定，着法列表要换回固定上限，
否则 `flex: 1` 会让它塌成 0 高度。

- 棋盘尺寸用 `aspect-ratio: 9 / 10` + `width: 100%` 自适应，格子的像素尺寸由容器推导，不做缩放控件

### 10.1.1 三个弹窗

都用**原生 `<dialog>` + `showModal()`**，不手写遮罩层 —— Esc 关闭、焦点陷阱、
`::backdrop` 遮罩都是白送的，也少掉一堆「忘了恢复 body 滚动」的坑。

| 弹窗 | 入口 | 职责 | 内容 |
|------|------|------|------|
| **局面库** `#picker` | 标题行，左 | **挑** | 分类页签 + 局面列表 + 退出残局 |
| **保存 / 导入** `#io-dialog` | 标题行，右 | **把框里那个 FEN 放哪儿** | 收进局面库 / 直接载入棋盘 |
| **重命名** `#rename-dialog` | 局面库「自定义」页签里每行的 ✎ | **改名字** | 一个输入框 + 保存 |

**`#io-dialog` 里只有一个 FEN 框，而且打开时填着当前局面**（并且全选）。
所以「存当前这盘棋」不需要单独的动作 —— 不动那个框就是它，覆盖掉就是别的局面。
一开始不是这样：那时拆成「存下当前局面 / 导入外部局面」两段，各带一个按钮，
**两个按钮同名**（都叫「存为自定义局面」），并排出现时看着像重复劳动。
界面上的重复，根子在数据上：「当前局面」和「粘进来的局面」本来就是同一个东西的两个来源。

**框里就是当前局面时，「载入到棋盘」置灰**（`main.js` 的 `syncLoadFenBtn`）——
那种情况点了等于没点。两条边界：

- 判等用**规范化之后**的 FEN（`validateFreeFen` 顺带做的），不直接比字符串 ——
  别处复制来的 FEN 尾部可能写成 `w - - 12 34`，其实载入进去是同一个局面。
- **解析不了的 FEN 不禁用。** 那种时候点一下会给出「哪儿不合法」；
  禁掉的话按钮就成了一个不会说话的坏按钮。规则是「**没有意义**才禁用」，不是「有问题就禁用」。

局面在弹窗开着时也可能变（玩家执黑，AI 那一步正好这时候落下来），
所以 `updateChrome()` 里带一个 `if (dom.ioDialog.open)` 的刷新 —— 关着就不白解析一遍 FEN。

重命名那个是**叠在局面库上面**开的（原生 `<dialog>` 支持嵌套模态，Esc 关的永远是最上面那层）。
改完局面库还开着、列表已经变成新名字 —— 用户能立刻看到结果。

**它为什么值得单开一个弹窗**，而不是 `window.prompt`：prompt 没地方显示
「名字最长 40 个字」这类原因，只能弹个 alert 再问一遍。「校验失败要带原因」是这个模块
从第一天起的规矩（见 §8.4），prompt 把这规矩废掉了一半。

**「复制 FEN」和「复制链接」都不在任何弹窗里。** 它们是「把当前局面拿出去」——
对当前局面的**即时动作**，和悔棋 / 翻转同类，所以做成棋盘下方工具栏上的按钮：
一点就复制，成功反馈直接给在按钮自己身上（文字短暂变「已复制」）。
给它们一个弹窗反而是多余的仪式感。

两者并列而不是收进一个「导出」下拉：它们是**同一件事的两种形式**（给对方一段文本
vs 给对方一条点开就看的链接），收进下拉会让常用的那个多一次点击。
代价是工具栏长了一点（7 个按钮），窄屏靠 `flex-wrap` 换行。

**为什么拆。** 一开始只有一个局面库弹窗，底部塞了「存当前局面」和一块
`粘贴 / 复制 FEN` 折叠区。问题是**三件事的方向根本不一样**：

| 里面的东西 | 干什么 | 最终去处 |
|---|---|---|
| 页签 + 列表 | **挑** | 局面库（本职） |
| 退出残局 | 切回标准开局 | 局面库（也是「换一局」） |
| 存为自定义局面 | 往库里加一条 | 和「挑」是两回事 → 独立弹窗 |
| 载入到棋盘 | **换当前局面，但不留下** | 需要那个 FEN 输入框，所以跟着上面走 |
| 导出 FEN / 复制链接 | 把局面**拿出去** | 方向相反 + 即时动作 → 工具栏 |

最后按**动作的性质**落到三处，而不是按「是不是和局面有关」硬凑在一起：

| 性质 | 位置 |
|---|---|
| **读** —— 挑一局来下 | 标题行左边的「局面库」 |
| **写** —— 往库里加东西 | 标题行右边的「保存 / 导入」 |
| **换** —— 换一个当前局面、但不留下 | 同上：框里那个 FEN →「载入到棋盘」（分享链接产出的是同一种局面） |
| **取** —— 把当前局面拿出去 | 棋盘下方工具栏的「复制 FEN」「复制链接」 |

> 拆分的**代价**：存完看不到列表变化（列表在另一个弹窗里，此刻没开）。
> 所以存 / 导入成功后会把页签预先切到「自定义」，提示文案也写明「在局面库的『自定义』页签里」——
> 用户下一步多半就是打开局面库去点它。

**分类用页签，不用下拉框。** 下拉框把「内置残局」和「自定义局面」混在同一个列表里，
看不出边界；页签让两者并列、随时能切。每个页签带一个**条数徽标**，
「我存过几条」不用点进去看。

**没有「全部」页签。** 三页并列、各看各的：内置的按来源分成「实用残局 / 适情雅趣」两页，
用户自己存的是第三页。「全部」会让「我现在在哪一页」没有答案。
代价是打开弹窗时不一定停在当前那一局所在的页 —— 所以打开时先把页签切过去
（不然高亮的那一行会藏在别的页签里）。

**页签下面有一个过滤框，只匹配名字，且只在当前页签内生效。**
「全部」页签被否掉之后，跨页签的检索就没了着落；《适情雅趣》又一下收成了 550 局，
光靠滚找不到具体一局。所以：

- **匹配名字**（`第473局 中外义安`），空白分隔的多个词是「与」。这是列表上唯一显示出来的文本，
  也是唯一同时带着局号与局名的地方。**不匹配 FEN 这类看不见的字段** —— 命中了用户也不知道
  为什么（「这行为什么会在这儿」），反而像 bug。
- **不跨页签搜**，否则页签和列表各说各话。跨页签的线索交给**页签徽标**：
  有过滤词时徽标显示的是各页的命中数，于是「搜「473」在当前页一条都没有」不是死路 ——
  徽标上直接写着这词在「适情雅趣」里有 1 条，点过去就行。
- **Esc 两级**：先清过滤词，框空了再按才关弹窗。拦截点是 `<dialog>` 的 `cancel` 事件 ——
  「按 Esc 关弹窗」是 dialog 的原生行为，不是 keydown 冒泡上去的，在输入框里
  `stopPropagation()` 拦不住。
- **过滤词不跨「打开弹窗」**：`closePicker` 清掉它，下次打开还是完整的一页。

**弹窗高度固定**（`.xq-dialog--picker { height: min(78vh, 700px) }`）。列表条数随页签与过滤词变
（550 / 8 / 0 条…），高度不固定的话弹窗会一会长一会短，连居中的位置都跟着跳；
固定之后只有列表内部滚动。

**页签表在 `js/endgames.js` 的 `TABS` 里**：加一页 = 加一项 `{ id, label, entries }`。
页签、条数徽标、列表内容、空态文案全从它来，界面那一侧不用改；
每条的 `category` 也由它所在的页签推出来，`tools/verify-endgames.mjs` 的
category 校验同样以这张表为唯一来源，不会出现「加了页签忘了加数据」或反过来。

用标准 ARIA tabs 语义（`role="tablist"` / `role="tab"` / `aria-selected`），
配 **roving tabindex** —— Tab 键整组跳过、左右方向键在组内切换。
这样「弹窗里要按几次 Tab 才能到列表」不会随页签数量增长。

**入口只有一个**：标题右边的按钮，它同时承担两个职责 ——
`局面库` 说明这里能点开什么，`· <局面名>` 显示现在在哪一局
（名字用强调色、标签用次要色，所以扫一眼先看到的是「我在哪」）。

> 最初做了**两个**入口 —— 这个按钮，加上标题下方一行可点的「当前局面」文本 ——
> 视觉上重复了。合并成按钮的正文之后，信息没丢，入口少了一个。

> **一个坑**：`global.css` 顶部的 `*, *::before, *::after { margin: 0 }` 重置
> 会把 UA 默认的 `dialog { margin: auto }` 一起干掉，弹窗就贴顶了。
> 必须在 `.xq-dialog` 上显式写 `margin: auto`。见 [`future-work.md`](./future-work.md) E8。

### 10.2 渲染（`renderer.js`）

- 棋盘用 **CSS Grid** 铺 9×10 个格子按钮（`.xq-cell`），交叉点用伪元素画线
- 棋子是绝对定位的 `<div>`（`.xq-piece`），`transform: translate(...)` 定位到格子中心
- **三层显式分层**（`z-index`）：棋盘线 `0` → 格子 `1` → 棋子 `2`；棋盘容器用 `isolation: isolate`
  把这三档的作用范围锁在棋盘内部。**不能依赖默认绘制顺序** —— 九宫斜线是 `.xq-board` 的伪元素，
  而伪元素在绘制顺序里等同于子元素（`::before` 最前、`::after` 最后），棋子又是 `appendChild`
  上去的、排在 `::after` 前面，于是红方九宫的斜线会盖住棋子，黑方却正常。踩坑记录见
  [`future-work.md`](./future-work.md) E7
- 移动动画：走子时**复用起点上那个棋子元素**，只改它的 `left` / `top`，让 CSS `transition` 接管补间。
  其余棋子全量重建 —— 因为重建时位置是在插入 DOM **之前**设好的，不会触发过渡，
  所以复盘跳转和悔棋时棋子直接出现在该在的位置，不会满屏乱飞。
  更完整的做法（按棋子身份匹配、跳转也带补间）见 [`future-work.md`](./future-work.md) B5
- 高亮：上一步的起点 / 终点（`.xq-cell--last`）、可走位置（`.xq-cell--target`）、
  可吃子的目标（`.xq-piece--capture`）、AI 提示（`.xq-piece--hint`）、
  被将军的将（`.xq-piece--checked`）

  **一条通用规则：凡是标在「目标格」上的东西，都要先问「这格上有没有棋子」。**

  格子高亮画在格子的背景上，而棋子是不透明的、盖住格子中心 ——
  所以**有子的格子，格子高亮完全看不见**（小圆点半径只有约 15px，棋子半径 28.5px）。
  于是分两类处理：

  | 目标格 | 标在哪 |
  |--------|--------|
  | 空 | 格子（小圆点 / 格子底色） |
  | 有子 | **棋子**（外圈） |

  「可吃子」和「AI 提示」都踩过这个坑，各补了一圈在棋子上。
  也可以反过来把点画得比棋子还大、让它露出一圈，但那样受格子尺寸限制
  （棋子半径 28.6px、格子半宽 31.1px），最多只能露出约 2.5px，太细。

  **三种「棋子外圈」的分工：**

  | 圈 | 颜色 | 用什么画 | 为什么 |
  |----|------|----------|--------|
  | 轮到我方 | 紫 `--xq-turn` | `outline` | 我方的**全部**棋子，数量最多 |
  | 可吃子 | 红 `--danger` | `outline` | 标在对方棋子上，与紫圈不会同时出现 |
  | AI 提示 | 琥珀 `--xq-hint` | `::after` | **必须用 `::after`**：提示的起点往往正是「轮到我方」的那个子，用 `outline` 会把它的紫圈顶掉，16 个紫圈里少 2 个看起来像渲染出错。`::after` 可以套在紫圈外面，两者共存（偏移 6px 让开紫圈和红环） |
- **轮到谁走**：那一方的**全部**棋子外圈加一道 2px 高亮圈（`.xq-piece--turn`）。
  只标将帅太不显眼 —— 满盘棋里找一个小圈很费眼，所以标一整方。

  几个刻意的选择：
  - **颜色是紫色 `#7c3aed`，而且要先想清楚"和谁比"。**
    圈画在**棋盘上**（棋子外沿之外），所以它要和棋盘底色比，不是和棋子比。
    棋盘是暖米色 `#f0d9b5`，最初选的黄色和它同一个色系 ——
    50% 透明度合成出来是 `#F2C65B`，还是「偏黄的米色」，对比天生就弱。
    紫色和米色是**色相对比**，一眼就能分开。同时它避开了所有已占用的颜色：
    红（棋子、被将军）、黑（棋子）、蓝（上一步）、青绿（可走位置）
  - **不透明比颜色更关键。** 原来的 2px + 50% 透明度，即使换成好颜色也还是细；
    现在是不透明的 2px
  - **粗细有几何上限，而且"不重叠"其实做不到。** 相邻棋子中心距 62.2px、棋子半径 28.6px，
    所以圈的外沿半径不能超过 31.1px 才不重叠。`偏移 2 + 宽度 3` 会到 33.6px（重叠 2.5px），
    宽度收到 2px 后是 32.5px（重叠 1.4px）—— **仍然重叠**，
    因为偏移 2px 本身就吃掉了大部分余量。
    想完全不重叠只能把偏移也降到 0（圈贴着棋子，看起来像加粗的边框），或者把棋子改小。
    当前选择是接受后排相邻棋子的圈轻微相接 —— 那反而强化了「这一整方都是待走的」这个信息
  - 红黑**统一用同一个颜色**，不用各自的方色 ——「高亮」表达的是「现在轮到这边」，
    而「这是红方的子」棋子本身已经说了。顺带省掉「红黑各一套 + 深色主题再各一套」四份颜色
  - 用 `outline` 而不是 `box-shadow` —— 后者已经被「上一步」和「被将军」占了
    （一个元素只能有一条 `box-shadow`），`outline` 不参与那套竞争，三者可以共存
  - 终局时撤掉（`status.type !== 'playing'`）—— 没有「轮到谁」可言了

> **试过又撤掉的方案**：给整块棋盘加一圈彩色外框（`.xq-board--turn`）。
> 想法是它「余光可见」，比盯着棋子看更省注意力。实际用下来觉得**过于抢眼** ——
> 棋盘本身已经是视觉主体，再给它套一圈亮色，反而把注意力从棋子上拽走了。
> 棋子圈的信息量已经够（哪一方、哪些子能动），不需要再加一层。
- 状态栏里的方名按方着色（红方红、黑方黑）。所以状态栏内容是**片段数组**而不是拼好的字符串
  （`setStatus('轮到', { side }, tail)`）—— 拼成字符串之后就没法只给方名着色了，
  而走 `innerHTML` 又不行（状态文案里混着用户输入，比如残局名）。终局时整行统一走危险色，方名让位
- 所有类名带 `xq-` 前缀（AGENTS.md 的模块隔离要求）
- **不做**：棋盘纹理图、棋子阴影细节、拖拽残影

### 10.3 交互（`interaction.js`）

- **点击选子 → 点击目标**（主路径，触屏也走这条）
- **拖拽走子**（鼠标增强，`pointerType === 'mouse'` 才启用，避免与触屏滚动打架，与 conway 的处理一致）
- 走子确认：目标格不在合法着法集合里则视为「改选另一个子」，不报错、不弹窗
- 键盘：格子是 `<button>`，Tab 可遍历；`Esc` 取消选中

### 10.4 主题

全部颜色走 `../global.css` 的 CSS 变量（`--bg` / `--card-bg` / `--text` / `--border` / `--accent` / `--danger`）。

**不需要监听 `themechange`** —— 这是选 DOM 渲染而非 Canvas 的直接收益（§3.2）。棋盘和棋子的颜色都是 CSS 变量驱动的。

棋子配色（红黑双方）需要在深浅两套主题下都可读，所以额外定义模块级变量并同时给出两套值：

```css
:root {
  --xq-red: #c0392b;
  --xq-black: #2d3436;
  --xq-board-bg: #f0d9b5;
  --xq-board-line: #8b7355;
}
:root[data-theme="dark"] {
  --xq-red: #ff6b6b;
  --xq-black: #e6e9ee;
  --xq-board-bg: #2b2a26;
  --xq-board-line: #6b6355;
}
```

### 10.5 界面用到的中文术语

统一用「执红 / 执黑」「挡位」「悔棋」「重开」「翻转棋盘」「着法」「提示」，不要混用「难度 / 等级」「撤销 / 回退」等同义词。

## 11. 持久化（`persist.js`）

- localStorage key：`chinese-chess:state`（**必须带模块前缀**，AGENTS.md 要求模块间不共享 key）
- 存的内容：`level`、`playerSide`、`mode`、`initialFen`、`moves`、`cursor`

## 12. 测试策略

规则引擎是唯一「错了会让整个项目看起来能用其实不能用」的部分，所以测试重点在这里。

### 12.1 `tools/test-rules.mjs`

| 测试 | 内容 |
|------|------|
| 初始局面着法数 | 红方 44 步（5 兵 + **24** 炮 + 4 马 + 4 车 + 4 相 + 2 士 + 1 帅）。炮各 12 步：红炮在 `(1,7)` 时向上 4 步、向下 1 步、向左 1 步、向右 5 步，再加上**以黑炮 `(1,2)` 为炮架吃掉它后面的黑马 `(1,0)`** 这 1 步。数「炮能走几步」时容易只数到炮架为止，把这一步漏掉 |
| 蹩马腿 | 四个方向各一个局面，马腿有子则该方向两个日字目标都不可达 |
| 塞象眼 | 田字中心有子则该目标不可达 |
| 炮的隔子吃 | 中间 0 子只能走空格；1 子可吃；2 子及以上不可 |
| 兵过河 | 未过河不能横走；过河后可横走；任何情况都不能后退 |
| 士 / 象区域 | 士出九宫、象过河均为非法 |
| 将帅照面 | 中间无子时该着法非法 |
| 应将 | 被将军时，非应将着法全部非法 |
| 将死 / 困毙 | 各一个固定局面，断言终局类型 |
| 三次重复 | 固定着法序列走三遍，断言判和 |
| FEN 往返 | 一批局面 `parseFen → toFen` 结果与原文一致 |

不依赖外部 perft 数值——象棋的 perft 基准值来源不一、易记错，用上面这些**逐个规则点**的断言更可靠，且失败时能直接指出是哪个规则错了。

### 12.2 `tools/test-notation.mjs`

固定局面 + 固定着法 → 断言记谱串。覆盖：进退平三种动作、马象士用目标纵线、车炮兵将用步数、前后重子、五兵的一二三四五。

### 12.3 `tools/verify-endgames.mjs`

见 §8.3，有问题时以非 0 退出码结束。

### 12.4 `tools/test-custom-endgames.mjs`

自定义局面是**唯一由用户输入驱动的数据**，所以它的测试重点不是「能不能存」，
而是**输入校验**：

- 每一类非法 FEN（解析失败 / 行数不对 / 照面 / 已终局）都要被拒
- 而且**每条都要断言失败原因非空** —— 界面要把原因显示给用户，
  说「不行」而不说为什么等于没说
- 将死和困毙走的是**同一条**理由（都已经终局），所以两条都钉住关键词，
  不能只断言「被拒了」—— 理由串了也能拒绝成功，用户看到的却是一句驴唇不对马嘴的话
- **「轮走方被将军、但解得开」要能通过**（见 §8.4），留个正例钉着
- 改名：**只动 `name`**（FEN / id / createdAt 都不许变），名字的规矩和新增一样（非空、40 字内），
  改不存在的 id 要返回失败而不是抛；**名字没变时不该写盘** —— 拿一台 `setItem` 必抛的
  storage 就能证出来（同名 → 成功，换个名字 → 失败）
- 损坏数据：非法 JSON / 版本不匹配 / 条目不是对象 / 单条 FEN 失效
- storage 不可用（隐私模式）与写失败（配额满）都不能抛异常

**「逐条校验」这条策略也要钉住**：列表里混一条坏数据，好的那些必须仍然读得出来。
这和 `persist.js` 的「整份丢弃」正好相反，是个容易在重构时被「统一」掉的差异。

### 12.5 `tools/test-share.mjs`

这个模块只有两个函数，但**两头都在处理别人给的输入**：生成链接时的 `href` 是浏览器给的、
可能带着上一次分享留下的参数；读取链接时的输入是**任意 URL**，别人可以改成任何样子。

后者尤其危险 —— 它直接决定 `initialFen`。一个没校验住的 FEN 会让对局从一个非法局面开始，
而那时候报错的地方离原因已经很远了。

重点：

- **生成**：清掉已有的查询串和 hash（否则会带出旧局面的残渣）；空格是 `%20` 不是 `+`
- **往返**：编出来再读回来，FEN 必须一模一样（含手工 `%20` 编码的情况）
- **区分「没带参数」和「带了坏参数」** —— 前者不是错误（`found=false`、`reason` 为空），
  后者要给出原因
- 每一类坏参数（空 / 不是 FEN / 行数不对 / 照面 / 缺将）都要被拒，且原因非空
- **钉住与 `validateEndgameFen` 的刻意不一致**：已经终局的局面，出题校验拒绝、分享校验接受；
  被将军的局面**两侧都接受**

### 12.6 AI 层（`tools/test-engine.mjs`）与冒烟（`tools/selfplay.mjs`）

AI 层**不做「搜了多少节点」「多少毫秒」这类断言**——它们随机器和时间波动。只钉住三类**稳定**的东西：

| 类型 | 例子 |
|------|------|
| 纯函数的数值性质 | 哈希的增量语义、评估的分值 |
| 只有唯一正确着法的局面 | 吃白送的子、被马盯上的车必须先跑 |
| 带对照组的开关 | 置换表开关前后最优着法一致；静态搜索开关前后「贪吃卒 / 不贪」；**将军延伸开关前后「看得见 / 看不见 5 层连杀」** |

新加的开关都按最后一行的形式测：**同一个局面、同一个基准深度，只翻一个开关**，断言结论变了。
连将杀探测同样有对照组（开着能不能找到 13 层连杀、关着找不到），外加一条「没有连杀的局面里
开关不改变结果、也不额外花节点」——防止它白花时间。

**自对弈冒烟负责单测覆盖不到的东西**：状态组合。让两个挡位真下一盘，检查全程着法合法、
对局能正常结束、没有死循环。这条策略的价值在 `future-work.md` 的 E3 记着 ——
那个 bug 54 条单测全绿，冒烟一次就抓到了。E9 是同一个道理的第二次。

## 13. 构建顺序

严格按依赖顺序，每步完成即可独立验证：

1. **规则层**：`position.js` + `rules.js` + `config.js` → `tools/test-rules.mjs` 全绿
2. **记谱层**：`notation.js` → `tools/test-notation.mjs` 全绿
3. **AI 层**：`engine.js` + `worker.js` → 命令行自对弈冒烟测试
4. **对局层**：`game.js`
5. **界面层**：`index.html` + `style.css` + `renderer.js` + `interaction.js` + `main.js` → 能人机对弈
6. **残局库**：`endgames.js` + `tools/verify-endgames.mjs` → 训练模式可用
7. **持久化**：`persist.js`
8. **收尾**：根 `index.html` 加卡片（图标建议 `🐘`，描述「中国象棋单机版，四挡 AI 与经典残局训练」）+ 根 `README.md` 加目录表 + 本模块 `README.md`

第 1~3 步全部是纯逻辑，能在 Node 里测完，不碰浏览器——这是刻意的：把「规则对不对」和「界面好不好用」分开验证。
